# 事故后规则升级流程

> 对应正文第 3 章 3.5 节“规则怎样升级”。来源：原第 4 章 4.14。

## 规则四要素

每条规则至少写清四件事：**失败形态、检查方式、替代动作和例外条件**。只写“不要出错”，既不能指导执行，也无法据此检查结果。

## 七类常见失败原因

排查常见失败时，可以先考虑以下七类原因：

1. 检查了错误的对象。
2. 多个执行者同时写入。
3. 只修复个别问题，而不修复机制。
4. 规则未生效。
5. 边界被悄悄放宽：例如超时上限、权限范围或检查阈值被改宽，却没有审批记录或告警。
6. 资源使用量无上限地增长。
7. 本地与远端行为不一致。

这些问题可能出现在各种系统中，并非某个产品独有。

## 检查器本身也要测试

- 除了核对检查结果，还要确认检查器确实执行了扫描，并记录执行次数、扫描数量和处理条数。
- 刚修复过一个失败样本时，撤销这项修复之后，该样本应再次被检出。
- 主动注入环境故障时，检查器应返回 `2`，而不能把检查器故障当成内容违规。

## 事故处理六步链路

处理一次事故不能停留在“改完提示词再试一次”，至少还应完成以下步骤：

```text
保留事故证据
  → 定位失败形态和责任边界
  → 先报数验证命中与误报
  → 再正式拦截或改成结构约束
  → 加入回归样本
  → 观察下一轮是否收敛
```

“先报数”是指新规则上线初期只统计命中和误报，暂不拦截任务；确认规则准确后，再正式拦截或改为结构约束。历史遗留问题可以记入基线，但基线中的问题应逐步减少，不能靠新增豁免来掩盖问题。

如果无法区分内容失败与基础设施失败，或者无法证明规则已经生效，就应继续由人工处理，或者让系统只生成草稿、保持影子运行（只运行和记录结果，不执行实际的外部动作）。
