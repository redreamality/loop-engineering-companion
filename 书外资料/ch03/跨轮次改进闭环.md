# 跨轮次改进闭环

> 对应正文第 3 章；单轮循环怎样由各项设施拼成闭环，见正文第 4 章 4.8 节。来源：原第 4 章 4.14。

五步公式回答的是“循环每转一轮，各项责任由谁承担、状态怎样交给下一轮”。要让循环在持续运行中越来越可靠，还需要跨轮次的工程闭环：每次执行和判定都有明确的目标与规则，并根据结果改进下一轮的做法。

```text
目标设定
  → 规则注入
  → Agent 执行
  → 机器判定
  → 证据记录
  → 失败归因
  → 规则升级
  → 下一轮执行
```

以正文 3.9 节的发票事故为例，即使已经阻止了重复付款，团队还要回答三个问题：修改了哪条规则？怎样证明新规则被实际加载？下一次遇到同类输入时，问题会不会再次漏过检查？

## 跨轮次工程闭环的交接证据与责任者

| 环节 | 要回答的问题 | 最小输出与通过证据 | 主要责任者 |
|------|--------------|--------------------|------------|
| 目标设定 | 要解决哪种不确定性，哪些决定仍由人负责？ | 成功标准、自动边界、不可逆动作清单 | 业务负责人 |
| 规则注入 | 规则在什么时候、以什么载体到达？ | 常驻规则、Skill、路径约束和版本记录；能证明本轮实际加载 | 控制面与规则负责人 |
| Agent 执行 | 执行者拿到了什么输入、权限和预算？ | 任务包、运行身份、工具结果和真实状态 | 执行面 |
| 机器判定 | 结果是通过、内容违规，还是检查基础设施坏了？ | `0` 通过且证据完整，`1` 内容或策略违规，`2` 检查器、环境或基础设施故障 | 验证器 |
| 证据记录 | 事后能否还原这次判断？ | 输入、规则、工具、扫描范围、处理条数、失败原因和外部状态 | 运行与审计负责人 |
| 失败归因 | 失败发生在路由、执行、判定还是环境？ | 失败类别、影响范围、接手人和下一项检查 | 值班人与领域负责人 |
| 规则升级 | 这次事故怎样减少下一次同类失败？ | 规则、检查器、结构约束或回归样本的变更，以及命中和误报证据 | 规则负责人 |

用发票任务串起此表：目标设定先说明自动化的边界；规则注入要能证明本轮采用了哪一版去重与检查要求；Agent 执行留下实际输入和工具结果。机器判定发现重复发票后，证据记录与失败归因要说明这张发票为何漏过了前面的控制，规则升级才能针对原因修改规则并加入回归样本。只改了规则文件，却无法证明下一轮加载了新版本，这项改进就还没有完成。

最后一列用于划分责任，不要求新设七个岗位。
