# 把栏目方法制作成自用 Combo（六步全文）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 9 章 9.12 节“把栏目方法制作成自用 Combo”；新版 6.5 只保留思路与验收，combo_draft_init/open/commit/status、manifest 与 runtime/combo.md 的六步细节在此保留。依据来源 SRC-FB-002。

### 把栏目方法制作成自用 Combo

每周都要重复说明来源格式、核验条件和输出结构，既费时间，也容易漏掉限制。第 6 章 6.5 节介绍过怎样安装、绑定和调用一个已有的包，这里把已经确定的栏目方法做成自己的包，让下一次会话可以直接复用。包的价值在于保留方法和资源，而不是保证模型每次都写对。

无需从空白的配置文件开始。先在对话里完成一期栏目，逐步纠正来源、事实台账、母稿和平台草稿的问题，确认最终结果符合要求，然后在同一个对话框输入：

> 把当前对话整理成combo。

也可以回到以前已经完成同类任务的会话，再提出这项要求。整理时保留最终采用的方法、模板和检查标准，把每期会变化的资料改为输入，不复制整段聊天历史，也不把失败尝试、客户原文和凭据带入通用包。助手应先列出准备保留的内容及仍需确认的地方，再制作和保存。

如果会话中已经形成一套完全固定的读取、筛选、计算和输出步骤，也可以输入“把当前对话整理成workflow”。Combo 适合让后续会话复用方法与能力；Workflow 适合把明确步骤交给程序直接执行。选用 Workflow 并不意味着所有语义判断都能取消，固定步骤的成本收益和模型调用边界见第13章。

这里需要先分清三个对象。普通 Skill 保存任务方法、指令与资源；Floatboat 的 Combo 是有身份、manifest 和运行内容的可安装能力包，需要在会话中绑定、加载后使用；Workflow 则表达工作流的步骤及执行关系。保存一份 `SKILL.md` 不等于提交 Combo，提交 Combo 也不会自动建立工作流或每周定时任务。第11章会用测试日志说明怎样调整这套方法的输入检查和验收规则，本例先做栏目方法包。

以下六步说明助手在整理与保存时应留下哪些结果，不要求读者亲自调用底层工具或从头填写配置。制作依据见来源说明 `SRC-FB-002`，尚未在本书样本上实机验证。前提是兼容的 Floatboat 环境已向当前助手提供草稿工具，并有有效工作区、会话上下文及本地文件访问权限。缺少这些条件就停在方法文件准备阶段。工具调用和文件编辑由助手承担，读者负责确定边界、检查产物和批准修订。

**第一步：整理可复用内容**

把栏目规则与每期素材分开。包内保存选题卡模板、事实台账模板、母稿与平台草稿要求、缺资料处理和验收样本；每期的来源快照、批准记录与成稿另放业务目录，不连同账号凭据打包。

输入至少包括来源 ID、版本、原文位置、许可、受众问题和已批准观点。输出约定为选题卡、事实台账、待核验母稿、平台草稿与缺口清单；母稿未批准时不继续平台适配。对上面的虚构产品资料，所有样本和输出都标注“教学虚构”，尤其不能把其中的云端运行假设写成 Floatboat 的能力。

**第二步：初始化草稿并保留身份**

请助手调用 `combo_draft_init`，名称可用“每周一项 AI 工作法”。应得到 `combo_id`、`draft_dir` 和制作指引。保存返回的身份，检查草稿目录确实存在，再按指引编辑。如果缺少会话上下文或初始化报错，就保留错误，不要自行编造 ID 和目录继续操作。

初始化已经打开了新草稿，不需要立刻再创建一个。中断后继续或以后修订时，使用原 ID 调用 `combo_draft_open`，并核对返回的身份与目录。被封装为不可编辑的包会被拒绝，不能通过修改标记绕开限制；本例只编辑本人拥有的草稿。

**第三步：完成 manifest 与运行说明**

`manifest.json` 说明这个包是谁、叫什么、当前版本以及访问策略。保留生成的 ID，按实际内容更新名称、说明和版本，访问模式保持 `owned`。不要手写一份看似完整却未经校验的 manifest 来替换生成结果。

`runtime/combo.md` 是助手运行栏目方法时读取的说明，不是本期文章。让助手写清：先查输入与来源，再生成选题和事实台账；等编辑批准大纲后起草，母稿获批后才做平台适配；遇到缺来源、许可不明或冲突数字时返回缺口，并停止受影响的后续步骤；最终只交付文件，不发帖。

配套模板与虚构样本放在运行目录内，并在说明中引用。同时约定每期的稳定任务 ID 和输出版本：重复输入时先查已有记录，返回原产物或待修订项，不覆盖已批准稿。这是一条需要验收的方法要求，去重要由包内方法自己保证。完成后应能直接看到上述文件，而不能只收到一句“规则已记住”。

**第四步：提交并查保存状态**

先检查包中没有真实客户资料和凭据，再让助手以原 ID 调用 `combo_draft_commit`，随后调用 `combo_draft_status`，核对活动包 ID、草稿目录、`save_state`、最近提交时间和 `last_error`。预期的保存状态为 `saved`，状态记录本身替代不了对打包内容的检查。

提交过程会校验 manifest、身份、owned 权限及 `runtime/combo.md`，打包运行内容，并在提供当前会话时尝试重载。如果字段不合法或缺少运行说明，就按错误修复原草稿，不要反复初始化新包。写包与会话重载是两个不同步骤：提交报错可能表示部分内容已保存，显示 `saved` 且没有保存错误也说明不了当前会话已经激活了新内容。接下来仍要核对实际加载的版本并调用样本。

提交成功之后，文章正确性和后台依赖就绪状态仍需另行确认；需要的依赖可能仍在后台准备或准备失败。本地提交属于本地保存，本例不提交市场。

**第五步：实际调用，再到新会话验收**

在当前会话中明确选用这个包，以正常样本运行一遍，要求助手报告实际使用的包 ID、版本和产物位置。先核对事实台账，再批准大纲与母稿，最后查看平台草稿。只有说明文件却没有任务产物，调用尚未完成；如果运行时报依赖或权限错误，应先处理运行条件，不要把它包装成资料不足。

随后新建一个普通会话，参照第 6 章 6.5 节的使用步骤，把已保存的包绑定到新会话，并核对它确已加载。旧会话提交时的重载只影响旧会话，新会话要单独绑定。只提供本期输入，不再粘贴整套制作提示词，检查这套方法能否独立复用。

至少要跑三组样本。正常资料应得到可回查的事实台账与分阶段草稿；删去许可或原文位置时，应列出缺口并停止相关起草或适配；原任务 ID 重复输入时，应指出已有产物，不重复生成，也不覆盖已批准版本。三组样本都不得触发发布。要逐组记录输入、实际输出、预期与通过情况，助手说“已通过”不足以勾选。

**第六步：根据失败修订**

若短帖漏掉限定词，先保留失败样本，再打开原草稿，只修订相应的规则或模板，更新版本、重新提交并复查状态。然后重新调用正常、缺资料和重复三组样本，确认修复没有破坏其他行为。交接时留下包 ID、版本、输入输出约定、样本结果与未验证项；以后接入真实渠道或增加工具时，另做授权和验收，不把本次自用成功扩大成自动发布成功。
