# 内容循环值班手册（含交班记录）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 9 章 9.16 节；值班六项工作、交班代码块与发布状态未知的处置在此保留。

## 9.16 把内容循环写成值班手册

内容循环即使平时运行顺利，也要提前安排好异常情况由谁处理。谁可以暂停排期，谁判断来源是否还能使用，谁联系作者或客户取得许可，谁决定是否公开更正，都应事先明确，不能出事后才到群里找人。

一份能照着执行的值班手册，至少要写清以下六项工作：

1. 值班人从状态台核对已批准、待发布、状态未知和观察中的内容，并记录数量和链接。
2. 来源监控人列出过去二十四小时内发生变化的来源，并注明受影响的主张和版本。
3. 运营负责人依据发布记录判断哪些失败可以安全重试，哪些必须先到平台核对。
4. 值班人按反馈类型分流，明确哪些由运营回复，哪些交给编辑、法务或产品负责人。
5. 栏目主编明确值班人可以暂停哪些队列，并写明恢复运行需要谁批准、提供哪些证据。
6. 交班人留下任务 ID、来源快照、当前状态和仍待决定的事项，接班人据此确认下一步操作。

值班人应核对状态台、来源快照、发布记录和交班日志，逐项写下当前状态、下一步操作、负责人和完成条件。只在聊天里回答问题，交班尚未完成。

日常使用的运行台不必展示所有内容数据，应优先列出需要人处理的事项：事实核验退回、许可到期、审批即将超时、平台状态未知、异常反馈和更正任务。已经正常完成的任务，只需汇总数量并提供链接。若把两百条“发布成功”放在最上面，值班人就可能漏看唯一一条“发到了错误账号”的记录。

**交班不靠聊天记录**

下午值班人发现一篇排期文章引用了正在更新的政策页面，但下班前无法确认新版含义。如果只在群里说“这篇先别发”，夜间调度仍可能照常运行。正确的交班需要改变系统状态：

```text
content_id: topic-184 / master-v6
current_state: fact_check
paused_jobs: web-publish-771, mail-send-412
reason: 权威来源在审批后更新，两个关键数字待复核
evidence: 新旧页面快照与差异位置
owner: 夜间编辑值班
next_decision: 重新核对适用日期，决定修订或取消
resume_authority: 栏目主编
deadline: 2026-08-15 09:00
```

聊天消息可以提醒同事，但要停止系统执行，还必须更新任务状态。夜间值班人接手时，就能查清哪些任务已暂停、谁有权恢复，无需重新调查整篇文章。

示例中的 `owner` 是负责人字段，表示当前负责推动下一步决策的人或值班角色，不是新的业务角色名称。`content_id`、`paused_jobs` 里的 `topic-184`、`master-v6`、`web-publish-771`、`mail-send-412` 都是任务 ID（选题、母稿、两个发布任务各自的稳定标识）；没有任务 ID，就无法可靠地追查记录或防止重复处理。

**发布状态未知的处置**

平台接口返回超时后，值班人按固定顺序处理：先用发布幂等键或发布 ID 查询，再按账号和时间窗口检查，最后才考虑重新提交。若平台既不能查询也没有可靠的幂等能力，任务应保持“发布状态未知”并交给人确认。此时“晚发十分钟”的损失，通常小于“重复向十万名订阅者发送”的损失。

内容循环还要明确暂停范围。单个平台异常时，只暂停该平台的队列；来源受到污染时，要检查所有依赖该来源的主张；账号凭证疑似泄露时，则暂停相关账号的所有写入操作。暂停范围过大会造成不必要的业务中断，过小则可能让同一问题继续传播。
