# 动手实践：把经营台账做成工作台（七步全文）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 8 章 8.9 节“动手实践”；新版 6.4 保留目标、三条样本与五条验收结果，初始化命令、七个步骤、交互测试、失败演练与打包交接全文在此。工程名 studio-ledger，第 9 章沿用。依据来源 SRC-FB-003。样本数据见本目录 samples/。

### 动手实践：把经营台账做成工作台

现在把控制台中最常查的两项做出来：逾期交付和待核实收款。目标是：打开页面便能看见异常，点开记录能找到依据，重启后核对备注仍然保留。第一版不付款、不催款、不修改正式账目，也不接入真实客户资料。

这条路线使用 **Floatboat 工作台模板 `floatboatai/floatboat-workbench-template`**，仓库地址为：<https://github.com/floatboatai/floatboat-workbench-template>。请从该仓库取得模板，并阅读所用版本的说明；若页面无法访问，先确认地址、账号权限或向维护者取得授权副本，不要用普通网页工程代替。以下命令依据本地实现与文档整理，尚未在本书案例中实机跑通，来源见 SRC-FB-003；模板版本变化时，以所取得版本的说明和脚本为准。

**第一步：准备三条虚构记录**

将练习的业务日期固定为 2026-09-30，按当地日期比较，避免第二天打开页面时预期变化。用一份虚构客户表、一份交付表和一份收款表关联出下面三条经营记录；它们是教学数据，与周恬的真实业务无关。

- **P01，客户青禾**：交付期限为2026-09-28，仍在进行中；应收6000元，确认到账0元，客户称已付但尚待核实。来源为客户C01、交付D01、发票I01和消息M01。
- **P02，客户远山**：交付期限为2026-10-03，仍在进行中；应收8000元，已确认部分到账3000元。来源为客户C02、交付D02、发票I02和到账记录B02。
- **P03，客户星渡**：交付期限为2026-09-25，已经完成；应收4000元，确认到账4000元，已结清。来源为客户C03、交付D03、发票I03和到账记录B03。以上金额币种均为人民币。

每条来源另存一段可打开的虚构原文，注明“教学样本”、版本及更新时间，例如统一使用 `2026-09-30T09:00:00+10:00`。字段包括稳定 ID、客户 ID、截止日、交付状态、币种、应收金额、确认到账金额、核对状态、来源 ID、来源版本、更新时间和核对备注。交付状态与收款状态分开；金额按整数分保存，页面再显示为元。剩余应收由应收减确认到账计算，不能由模型补写。

**第二步：创建独立练习工程**

先从上述模板仓库取得一份独立、未初始化的工程副本，并记录所用提交号或发布版本；不要在已有业务工程上重新初始化。让助手读取其中的 `README.md`、`AGENTS.md` 和工作台 Skill，核对 `package.json` 中的环境要求与脚本。本例所核对的环境是 Node 22.16+ 的 22.x 及 pnpm 10.22.0；如果所用模板的要求不同，先按该版本说明调整，不直接照抄。进入该副本的工程根目录后执行：

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm workbench:init -- --registry studio-ledger --name "经营台账" --description "核对逾期交付与待核实收款"
```

初始化应更新 `app/manifest.json` 的应用身份和名称。出现 `ALREADY_INITIALIZED` 就停止重复初始化，检查是否误用了已有工程，不删除旧身份重来。随后让助手把上述字段、样本、只读边界和验收条件写入 `app/REQUIREMENTS.md`；不能把“工程已创建”记成“工作台已完成”。

**第三步：实现页面与持久化**

让助手在 `app/` 中实现列表、异常筛选、来源详情和核对备注编辑。业务事实保持只读，只有练习备注可以保存。页面通过应用接口访问服务，由服务操作 SQLite，不让浏览器直接执行 SQL。按模板迁移机制建立业务表，样本按稳定 ID 只导入一次；再次启动不能覆盖已有备注。

这一轮应得到页面源码、服务接口、数据库迁移和测试，并同步维护 manifest、工程说明与设计说明。要求助手增加对应交互测试：切换筛选能看到正确记录，来源详情能打开，保存失败时显示失败且保留待保存文字。保存成功必须以服务返回为准，不能只改变按钮文字。第一版本地使用，manifest 不声明未用到的 Host 能力，也不把数据库或凭据放进源码。

**第四步：检查后打开预览**

```sh
pnpm workbench:check
pnpm test
pnpm test:e2e
pnpm workbench:preview
```

先让助手把上一阶段要求的浏览器交互用例放入 `app/e2e/`，并按模板的测试配置准备可用浏览器；测试使用独立的虚构数据，不连接真实客户业务。`pnpm test` 运行脚本测试，`pnpm test:e2e` 才运行该目录的浏览器用例，二者分别保留结果。浏览器缺失或测试没有执行时，不能只凭脚本测试成功就宣称交互通过。

前三项命令成功后，再打开预览命令输出的完整地址，不要自行猜测端口。`pnpm workbench:check` 负责核对声明、依赖、类型和构建；测试只能证明实际覆盖到的断言。页面能够打开以后，还需另外检查筛选、来源和保存行为。命令失败时保留错误及退出码，修复后从失败步骤重跑，不继续宣称后续已通过。

**第五步：手工核对三类结果**

在固定日期下，逾期交付应只有 P01：P02 尚未到期，P03 虽已过截止日但已经完成。待核实收款应包含 P01，不能因消息 M01 声称已付款就将确认到账改成 6000。P02 剩余应收应为 5000，P03 为 0；剩余应收不等于逾期应收，未提供付款到期日就不能计算后者。

逐条打开来源，核对 ID、版本、时间与原文是否对应。再暂时移走一份练习来源，页面应显示“来源缺失”，不能把空白当作金额为零或核对通过。这里的“应”是验收标准，只有实际观察并记录后才能改写为通过。

**第六步：刷新、重启与失败演练**

给 P01 保存“等待核对到账凭证”的备注，刷新页面；再用 Ctrl+C 停止预览，从同一工程重新启动，确认备注和三条记录仍在。模板把预览数据保存在 `.local/data/`，不要为了消除错误清空它。刷新后备注仍在，只证明刷新这一项检查通过，不能代替进程重启测试。

让助手在隔离测试中模拟一次保存失败，确认旧记录未被错误覆盖、页面未报成功；再检查空列表与服务不可达显示不同状态。修改并保存源码后，如果检查失败，预览可能仍在展示旧版本；此时应核对终端状态，不能把旧页面当作新修改已经生效。涉及 Host 的扩展调用未连接时会返回 `HOST_NOT_CONNECTED`，本地台账不应因此伪造同步成功。

**第七步：交接工程，不混同数据搬迁**

完成上述核对后运行 `pnpm workbench:pack`，应在 `artifacts/` 得到 `.fbworkbench` 文件及终端报告的路径；已有同名文件时使用新的输出名，不强行覆盖。不要使用生成 npm 归档的 `pnpm pack` 代替它。

交接清单保留工程版本、启动方法、字段口径、样本、测试结果和未通过项。默认打包不带预览业务数据，SQLite 数据备份应另行安排并做恢复核对。客户端导入、信任授权和导入后的数据验收是下一阶段，本例未验证成功。到这里，完成条件是本地练习可运行、结果可核对、失败不误报，而不是已经部署了一套经营系统。
