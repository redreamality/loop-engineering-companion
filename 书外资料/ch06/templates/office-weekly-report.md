## 周报自动生成循环


周报案例在前面几章反复出现，这里把前面介绍的做法整理成可复用的模板。

**数据范围比文风更重要**

周报最常见的问题是时间范围混乱、项目遗漏、旧风险被当成新进展、临时讨论被写成承诺。林岚即使拿到一份文字完整的周报，也仍需知道三个项目是否属于同一统计范围。表 7-3 沿五步固定业务周、项目范围和来源快照，使生成、验证和补跑使用同一批事实，之后才有可靠的内容可供润色。

**表 7-3  周报循环的数据冻结、来源与调度**

| 步骤 | 设计 |
|------|------|
| 发现 | 系统按团队、业务周和周报类型创建唯一任务，规则版本绑定在任务上，并固定时区与周界限；范围变化时生成新任务，不覆盖旧周报 |
| 交付 | 系统汇总看板变化、获批会议决定和上周未关闭风险；每条信息都带来源、更新时间和所属业务周，缺少来源的字段留空 |
| 验证 | 验证器检查项目覆盖、数据范围、数字引用、风险状态和客户承诺；任一来源缺失就标出缺口并阻止对应内容放行 |
| 记忆 | 控制面保存已发布周报、来源快照、人工修改和连续未关闭风险；发布后的更正不改写原版本 |
| 调度 | 周期结束后运行；关键来源未到齐就等待，超过截止时间只能带缺失清单起草，并提醒负责人补充 |

发现时固定的业务周限定“报哪段时间”，交付中的更新时间说明“各项目资料新到哪里”，调度则决定缺资料时等多久。假如一个项目未及时更新，另两个项目的文字写得再完整，也不能消除这个缺口；到截止时只能带缺失清单起草，不能让 Agent 补出该项目的进展。已确认结果可以保留，但缺失状态也要跟着草稿进入验证。

冻结范围不意味着发布后可以悄悄补写原稿。迟到资料只能用于更正原周报，或留到下一业务周处理，并保留原版本。下面的任务包与“三个时间”约定，就是为了让周一补跑仍能还原上周的事实，而不把当前看板状态混进去。

周报任务包至少要明确并固定以下要求：

```text
目标：在固定业务周内生成带来源的周报草稿
输入：团队、business_week_id、冻结的看板与会议来源快照
上下文：团队时区、周界限、上周未关闭风险和获批决定
约束：无来源字段不得写成事实；发布后迟到资料只能生成更正或下一周任务
成功标准：每个项目、数字和风险都能回指来源与更新时间，缺失项显式列出
回传：status、changes、risks、decisions_needed、missing_sources、source_refs、version
```

**任务包中的三个时间**

周报至少区分三个时间：业务周期、资料更新时间、实际运行时间。周五 15:00 生成的周报，可能有项目在 16:00 才完成更新；周一补跑时，数据库中的当前状态又已经变化。任务包要冻结“本周”范围，并记录每个来源读取时间。周一补跑仍使用原业务周和冻结快照；周一的新变化进入下一业务周。

**验证矩阵**

固定了来源范围，还需要判断这些资料在周报中是否被正确使用。三个项目都有段落，只能证明表面覆盖，不能证明数字有依据，更不能证明一项提议已获批准。表 7-4 把这些判断拆开，使验证失败后能退回相应内容，或阻止整份周报发布。

**表 7-4  周报验证矩阵：检查项、方法与失败行为**

| 检查 | 方法 | 失败行为 |
|------|------|----------|
| 三个指定项目是否都有结果 | 集合规则 | 缺失项显式列出，不静默生成 |
| 数字和日期是否有来源 | 字段与引用核对 | 退回对应条目 |
| 延期是否被弱化 | 规则加语义验证 | 提高风险等级并转人工 |
| 提议是否写成决定 | 对照会议证据 | 改为待确认 |
| 客户承诺是否获批 | 权限与审批记录 | 阻止发布 |

这些检查不能相互抵消。三个项目都有文字，可以通过集合检查；其中一句把会议提议写成承诺，仍需回到会议证据改为待确认，并核对相应批准。旧风险、当前状态和本周变化也要分别找到来源，否则把旧风险换一种措辞，就可能让管理者误以为本周出现了新情况。

失败后的处理范围取决于问题：“数字和日期”一行可以退回有问题的条目，“客户承诺”一行则阻止发布，不能删掉警告后继续发送。矩阵规定了最低检查责任，缺证据时必须保留缺口，不能用其他项通过来换取放行。只有先把问题内容隔离、核实低风险部分，才有条件讨论后面的低风险部分简化放行。

周报流程稳定后，低风险部分可以合并成一次例行批准，由林岚确认后发布，“没有更新”也要作为状态展示。系统不应为了让周报看起来完整而编造工作活动。

**故障演练与指标**

- **资料迟到**：在资料截止时间之后补入一个项目的更新，周报仍按冻结快照生成，并按本文件末节“业务周冻结”的方式标明缺失项、等待或请负责人补充；发布后才到达的资料进入更正任务或留到下周，不改写已发布版本。
- **周一补跑**：周一重新运行上周任务，仍使用原业务周和冻结快照；周一看板上的新变化不得写进上周周报。
- **缺少项目更新**：移除一个项目的更新，周报显式列出缺失项目，不静默生成，也不补写看似完整的进展。
- **提议写成决定**：样本中放入一项只是会议提议的事项，验证必须把它改为待确认，不能当作已批准的决定发布。
- **未获批的客户承诺**：草稿出现未经审批的客户承诺时，阻止整份周报发布，不能删掉警告后继续发送。

项目覆盖率、事实错误数、风险漏报、人工修改率、来源缺失率、端到端时延和每周人工投入是核心指标。还要追踪那些长期未关闭、每周却只被换种说法重复描述的风险。这通常说明流程中还没有人采取措施处理这些风险。


## 7.14 周报的业务周冻结

上文提到，周报任务包要冻结业务周并区分三个时间。本节具体说明怎样记录这些时间，以及怎样处理迟到资料。

**先定义“本周”**

不同团队的工作周、时区和结算日不同。周报任务创建时保存：

```text
business_week_id: 2026-W33-team-a
start_at: 2026-08-10T00:00:00+10:00
end_at: 2026-08-14T17:00:00+10:00
data_cutoff_at: 2026-08-14T15:00:00+10:00
generated_at: 2026-08-14T15:12:00+10:00
```

周一补跑仍使用原时间范围和冻结快照。当前看板已经进入新一周，不能直接查询“现在状态”替代历史变化。

**区分变化、状态和解释**

项目“当前完成 70%”是状态，“本周从 55% 到 70%”是变化，“因为供应商提前交付”是解释。三者来源不同，周报任务包应分字段提供。Agent 不能仅凭两个状态数字自行编造变化原因。

**迟到资料**

截止前仍缺少某个项目的更新时，可以等到规定时限，也可以发布标明缺失项的草稿，或请负责人补充。系统应记录采用了哪种处理方式。资料在发布后才到达时，应创建更正任务，或留到下周继续处理，不能直接改写已发布版本而不留记录。

**周报不应只描述活动**

每项信息都应回答管理者关心的问题：取得了哪些可验证的结果，哪些风险需要作出决策，下周哪些计划所需的资源已经落实。Agent 不能为了丰富报告，把会议次数和消息数量写成进展。

试运行时，用过去四周实际发布的周报作对照，回测是否遗漏项目、弱化风险，或把旧活动重复写成新进展。历史稿也不是绝对标准，评测时既要参考人工判断，也要核对原始资料。
