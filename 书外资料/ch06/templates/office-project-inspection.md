## 项目进度巡检循环


**适用边界**

巡检循环找出需要关注的项目状态，并生成核查清单或提醒草稿。它不应仅因任务逾期就评价个人绩效，也不应把看板没有更新直接等同于工作没有进展。

目标示例：

> 每个工作日 17:00 扫描指定项目：找出临近截止但未完成、三天无状态更新、阻塞其他任务、关键里程碑偏离的项目；合并同一问题的连续信号，引用原始任务和依赖关系，先向项目负责人生成确认清单，确认后再升级风险。

**五步设计**

同一项目连续三天没有更新，可以每天被扫描发现，却不该每天生成一条新的正式风险。表 7-6 将信号归并、状态核对、负责人确认和提醒时间连起来，既保留待调查的变化，也避免把尚未证实的问题反复通知出去。

**表 7-6  项目巡检循环的信号确认与提醒节流**

| 步骤 | 设计 |
|------|------|
| 发现 | 系统扫描任务、里程碑和依赖关系，并按项目和风险类型归并信号，政策版本绑定在活动记录上；相同风险只建立一项活动记录 |
| 交付 | 系统提供当前状态、变更历史、依赖、负责人和日历；项目数据只允许读取，提醒先生成草稿，不直接通知负责人 |
| 验证 | 验证器核对日期、状态和依赖，并区分“未更新”“确认延期”“外部等待”；无法确认的信号停在待核对 |
| 记忆 | 控制面保存已确认风险、负责人回应、静默期和关闭证据；未确认信号不升级为正式事实 |
| 调度 | 默认在日终扫描，重要里程碑可事件触发；同一风险在静默期内不重复提醒，影响增大或持续未响应才升级 |

发现层把相同风险归入一条活动记录，验证层再区分“未更新”“确认延期”和“外部等待”。如果负责人说明正在等待客户材料，系统需要保存回应和复核时间；下一次日终扫描应更新证据，不能把同一个等待事实重新包装成一条新风险。记忆保留回应，调度遵守静默期；缺少回应记录或不遵守静默期，都会增加重复催办的风险。

静默也有边界：影响增大或持续未响应时，应按既定政策升级，不能因为已建过记录就永久忽略。未确认信号仍须留在待核对状态，不能进入正式风险台账或用于绩效判断。下面的任务包要同时带上证据和确认问题，使负责人能纠正状态，而不只是收到一句“项目有风险”。

项目巡检任务包至少要明确并固定以下要求：

```text
目标：扫描指定项目并生成待确认的风险核查清单
输入：项目 ID、任务与里程碑快照、依赖关系、负责人目录
上下文：看板版本、业务周期、静默期和升级政策
约束：只读项目数据；未确认信号不得升级为事实或用于绩效；提醒先留在草稿
成功标准：每个信号有最后更新时间、截止日期、依赖和确认问题；重复风险只保留一条活动记录
回传：signals、confirmation_items、risk_status、reminder_draft、next_review_at、evidence_refs
```

**从信号到风险要经过确认**

“三天未更新”只是一个需要核查的信号，不能据此直接判定存在风险。任务可能已经完成，只是负责人忘记更新；也可能是负责人休假，或需要等待其他团队完成前置工作。循环应先生成带证据的核查项，包括最后更新时间、截止日期、依赖任务和待确认的问题。

负责人可以选择“状态已更新”“风险属实”“等待外部”“日期需调整”或补充说明。只有经过规则或负责人确认，信号才进入项目风险台账。确认环节同时减少误报，并阻止 Agent 的推断进入正式记录。

**提醒需要节流**

每天对同一风险重复提醒，人很快就会忽略这些通知。每项风险应记录最后提醒时间、当前负责人、下一次复核时间和升级条件。高风险事项可以缩短静默期，低风险事项等待状态变化后再提醒。

**故障演练与指标**

- **陈旧数据**：让看板沿用已失效的时区设置或过期的同步时间，风险候选应保持待核对状态；只有重新读取当前状态并确认到期后才允许提醒，同时记录数据版本和读取时间。
- **依赖循环**：构造 A 等待 B、B 又等待 A 的依赖，系统生成一项依赖环风险并交给流程负责人，不能向两名执行者反复催办。
- **负责人离职**：移除原负责人后，停止发送旧提醒；任务进入待重新分配状态，并保存组织目录版本和替班负责人的信息。
- **批量误报**：当同一规则在短时间内产生大量相似候选时，控制面暂停批量通知，抽样核对候选及其使用的规则版本，并记录已发送数量，用于判断影响范围。
- **状态恢复**：项目系统不可用时记录扫描失败情况和重试时间范围；恢复后从上次成功游标补扫，不能因为扫描失败就报告“今日无风险”。

真实风险发现率和误报率用于判断信号是否可靠；确认时延和长期未确认的事项，用于判断负责人能否及时处理；重复提醒数用于检查节流是否有效；关闭时长与状态补全率则反映处置结果。不能仅凭提醒数量判断系统是否有用。

## 7.16 项目巡检的提醒政策

上文指出，从信号到风险要经过确认，提醒也需要节流。本节说明这些要求怎样落实为具体的提醒政策。

**发现信号后不立即通知**

三天未更新、临近截止、依赖阻塞都是需要核查的候选信号。系统先合并同一项目下相同风险类型的信号，再查询当前状态和负责人。确认任务仍处于活动状态后，才生成核查项。

**一项风险只有一条活动记录**

```text
risk_key: project-42 + milestone-delay
policy_version: policy-v3
status: awaiting_owner_confirmation
first_seen_at: 2026-08-11
last_evidence_at: 2026-08-14
last_contact_at: 2026-08-13
next_review_at: 2026-08-17
escalation_at: 2026-08-18
```

每日扫描时只更新证据，不为同一风险每天创建新提醒；风险关闭前只保留这一条活动记录，不因跨周、换扫描批次或政策升级另建，政策升级时在同一记录下改用新版本并重新评估。负责人回复“等待客户材料，下周一复核”后，系统保存下次复核时间，在此之前保持静默。

**根据风险影响和未响应时长决定是否升级**

是否升级风险，应依据里程碑的重要性、依赖数量、距离截止时间还有多久、风险是否已经确认，以及负责人未响应的时长。不同项目可以采用不同的政策版本。

**避免绩效误用**

任务未更新，可能只是员工不习惯及时在系统中记录，不等于没有开展工作。巡检数据用于确认状态和处理风险；若要用于绩效评价，需要另行制定政策，向员工说明评价依据，并明确由谁负责。不能在员工不知情的情况下，把补充数据的循环用于评价员工。

**两周试运行**

第一周只生成待核查事项，与项目运营人员的判断比较；第二周向少量负责人发送经审批的提醒。统计真实风险、误报、重复联系、回应时间和状态补全情况。若误报集中于某类项目，应先检查数据并调整规则，不能让负责人自行忽略越来越多的错误提醒。
