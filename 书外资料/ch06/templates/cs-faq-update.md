# 常见问题（FAQ）持续更新循环（落选模板）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 10 章 10.4 节；知识候选与批准内容较薄，落选后全文保留在此。表格沿用原书编号。

## 10.4 常见问题（FAQ）持续更新循环

Agent 不应仅凭从工单中归纳出的内容，就直接改写 FAQ。客户问题可以帮助团队发现知识缺口，但正式答案仍要经过产品、政策和内容责任人确认。

**从问题簇到知识候选**

发现层定期聚合已脱敏工单，找出高频问题、现有答案无法解决的问题以及客服反复手工补充的部分。聚合时保留工单数量、时间范围、涉及产品和代表性表达，但不要把个人信息带进知识候选。

客户反复询问为什么不能取消订单，可能是答案难找，也可能是现有条目没有写清适用条件。工单频率本身不能告诉团队应采用哪种解释。表 10-3 将“发现知识缺口”和“批准正式答案”分开，并要求保存来源与版本，以便政策变化后能找回需要复核的条目。

**表 10-3  FAQ 知识候选的发现、批准与失效复核**

| 步骤 | 设计 |
|------|------|
| 发现 | 从已关闭工单、搜索失败和人工反馈中形成知识缺口候选 |
| 交付 | 提供问题簇、当前 FAQ、产品文档和政策；只使用获准数据 |
| 验证 | 产品事实、政策、适用范围、发布日期和链接由责任人确认 |
| 记忆 | 保存知识条目版本、来源、批准人、适用产品和失效日期 |
| 调度 | 周期性审查候选；产品或政策变化时触发受影响条目复核 |

问题簇只能说明知识可能缺失，不能直接成为正式答案；获批条目必须保存适用范围、来源、批准人和失效日期。

例如，“为什么不能取消订单”反复出现时，发现环节只负责将这类问题归为一个问题簇，交付环节还要提供对应的产品资料和政策；只有责任人确认适用条件后，答案才能成为正式知识条目。以后政策发生变化，调度环节应根据记忆环节保存的来源与适用范围找到旧条目，不能等客户再次投诉才发现答案已过期。

**知识条目需要版本和适用范围**

“订单可以在发货前取消”可能只适用于某个地区、产品或支付方式。FAQ 条目应包含适用条件、例外、来源和更新时间。客服 Agent 检索到条目时，还要检查它是否适用于当前客户和订单。

不能不留记录就覆盖旧答案。发布新版本后，要保留变更原因和生效时间；正在审批的回复若引用旧政策，要标记为过期并重新验证。

**用未解决率验证 FAQ**

评估 FAQ 的价值要同时看浏览量、客户阅读后仍提交工单的比例、客服需要补充说明的频率，以及错误引用和条目过期的情况。若一篇 FAQ 访问量很高，同类工单却没有减少，可能是答案不清楚、入口设置不合适，或业务本身存在问题。
