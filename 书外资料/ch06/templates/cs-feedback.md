# 客户反馈处理循环（落选模板）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 10 章 10.5 节；四种材料分层与内容模板的素材分层同构，落选后全文保留在此。表格沿用原书编号。

## 10.5 客户反馈处理

评论、调查、退货原因和客服会话，可以帮助团队发现需要改进的问题。客户反馈循环要把这些分散的表达整理成有证据、有人负责、能追踪处理结果的问题记录。其中最容易出错的一步，是把“多位客户说了相似的话”直接写成“产品确实存在某种缺陷”。

**从客户原话到已确认问题**

这个过程会留下四种材料：原始反馈、反馈片段、主题候选和已确认问题。它们分别回答“客户说了什么”“其中包含哪些诉求”“哪些表达可能在说同一类问题”和“经过核查，究竟确认了什么”。下面沿用本章开头的咖啡机咨询说明它们的区别。

**原始反馈**是客户的完整表达，例如“我上周买的咖啡机还没到，页面明明写着次日达。再不送来就给我退款。”系统保留来源、时间、涉及产品和允许使用的范围。此时能确定的是客户作出了这些陈述；是否超时、是否适用次日达、能否退款，都要另查订单和政策。

**反馈片段**是从原话中拆出的一项问题、需求或赞扬。上面的反馈可以拆成“客户称尚未收到商品”“客户认为页面承诺次日达”和“客户提出退款诉求”。用于分析的片段应先脱敏，并保留有权限者可回查的原文引用。拆分用于分别分析各项诉求；一条反馈拆出的三个片段按一条反馈计数。

**主题候选**是把相似片段归为一组后形成的待核查描述。例如，系统可以将相关表达归入“客户反映配送未达到页面承诺”。候选中要保留样本、时间范围、渠道、涉及商品和归纳版本。这个名称描述的是反馈中的共同点，尚不能据此断言仓库或承运商出了故障，也不能把某个渠道的投诉比例当成全部订单的问题比例。

**已确认问题**由产品或运营负责人核查后建立。对于上述候选，负责人需要回查客户原话、对应订单、物流记录和当时适用的页面承诺，再写明已经证实的问题及其影响范围。确认配送未达到承诺之后，还要查清延误原因；根因未明时，应继续保留待调查项。证据不足的候选仍可进入调查队列，但不能标为已确认。

**五步循环怎样处理这些材料**

四种材料描述的是信息经过了怎样的整理和核查；发现、交付、验证、记忆、调度则说明循环怎样组织工作，两者不一一对应。咖啡机投诉归入一个主题后，团队仍需要知道谁来回查订单、哪些结果能写入正式问题记录，以及下轮收到相似投诉时如何续接。表 10-4 按五步列出这些分工与产物。其中，“交付”是把本轮分析所需的材料交给执行者，“记忆”从接收反馈时就开始保存记录，“调度”决定何时启动或继续处理。

**表 10-4  客户反馈处理的五步分工与产物**

| 步骤 | 具体做什么 | 留下什么结果 |
|------|------------|--------------|
| 发现 | 从获准渠道接收新反馈，按来源事件 ID 识别重复采集，用订单等业务对象标识关联记录；缺少稳定标识时交人工复核，不凭相似措辞自动合并 | 可回查来源的反馈清单，标明重复记录和待核查记录 |
| 交付 | 向 Agent 提供已脱敏片段、分析的时间与商品范围，以及已有主题和问题记录；Agent 据此分类、归并相似表达，不读取不必要的身份信息 | 带样本引用的主题候选，以及它与已有问题的可能关联 |
| 验证 | 产品或运营负责人回查样本，核对订单等业务数据，检查重复计数、渠道偏差和适用范围 | 具名核查结论：确认为问题、补充调查，或不成立；同时写明证据和仍未知的事项 |
| 记忆 | 持续保存原文引用、片段与主题的关联、主题版本、核查结论、负责人和处置进展 | 可追溯的问题记录；后续反馈可关联到已有记录，无需每轮重新建项 |
| 调度 | 按周期整理普通反馈，按预设条件安排评审；收到严重安全或质量信号时立即通知责任人，处置后安排复核 | 下一次任务的触发条件、负责人和复核时间 |

例如，下一轮又收到咖啡机配送投诉时，系统先识别它是新反馈还是旧消息被重复采集，再查是否与已有主题或问题有关。发现环节的去重影响样本计数，交付环节的归并只提出关联，验证环节才决定能否纳入同一已确认问题。新反馈可以补充原记录的证据，但若涉及不同地区、商品或承诺条件，就需要重新核查范围。记忆环节保存这次判断，下轮就能续接已有记录，也不会仅凭措辞相似就沿用旧根因。

普通候选何时进入评审，应事先约定观察时间、去重后的反馈数量、涉及订单范围和最低证据要求；达不到条件时，保留候选并注明还缺什么材料。严重安全或质量信号则立即进入人工调查，不等待样本积累，也不等待本轮聚类完成。立即进入调查只代表提高处理优先级；是否存在问题、影响多大、原因是什么，仍须分别核查。

**频率与严重程度分开**

一个低频安全问题可能比一百条配色建议更紧急。主题排序至少考虑频率、严重程度、受影响客户、业务阶段、趋势变化和证据可信度。模型可以帮助整理，但严重程度标准由业务和专业责任人定义。

**跟踪项要回到反馈来源**

一个问题列入产品路线图后，仍要跟踪到处理完毕。确认问题后，负责人要记录处理决定、预计复核时间，以及何时、向谁反馈结果。修复后，由验证者核对证据，决定关闭问题还是继续调查；不能仅凭执行者填写“已完成”就结束跟踪。适合通知客户时，系统依据原反馈关联的记录生成受影响用户清单和消息草稿，由有权限的人批准。即使内部决定不能公开，也要保留处理状态和原因，供后续客服查询。
