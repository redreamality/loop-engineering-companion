## 报表审批循环


**适用边界**

报表审批循环读取结构化报表，运行确定性校验，生成异常说明，并把需要决定的部分送给有权限的审批人。模型可以解释异常和整理证据，不能替代金额计算、权限校验和正式审批。

目标示例：

> 每月财务报表锁定后，检查字段完整性、期间一致性、汇总关系和预设异常阈值；为失败项生成带单元格或记录引用的解释草稿；无异常报表进入指定审批队列，有异常报表先退给编制人；任何审批状态只由授权人的明确动作更新。

**五步设计**

报表中的数字可能算对了，期间却用错；异常说明可能听起来合理，却没有原因证据。审批人还要防止自己签的版本与最终提交的版本不同。表 7-5 分别安排确定性检查、Agent 解释和人工审批，并把它们绑定到同一份锁定报表，避免一个环节的成功掩盖另一个环节的缺口。

**表 7-5  报表审批循环的版本、验证与签字责任**

| 步骤 | 设计 |
|------|------|
| 发现 | 系统在报表版本锁定后创建任务，并用组织、报表类型、期间和版本共同标识任务；同一版本重复触发时复用原任务 |
| 交付 | 系统提供只读报表、口径说明、确定性规则和历史对比范围；模型只能读取和解释，不能修改原表 |
| 验证 | 验证器先运行公式、类型、勾稽和权限检查，再让 Agent 解释异常；审批人必须核对每项解释的证据 |
| 记忆 | 控制面保存报表哈希、规则版本、异常、修改版本和签字记录；任何版本变化都使旧审批失效 |
| 调度 | 月结或数据锁定后触发任务；数据未齐就等待，不能用旧报表冒充本期，超时转回编制人 |

表中的顺序要求先确定可核对的规则结果，再让 Agent 整理异常证据。计算能说明变化有多大，却不能单独证明变化的原因；审批人需要分别核对数值与解释的来源。缺少解释依据时，系统应留下待调查问题，不能让一段流畅说明替代尚未完成的核查。

编制人修正报表后，原计算、异常说明和批准都可能不再对应当前数据，所以记忆中的报表哈希必须与后续动作一致。这一要求也限制了模型的角色：它可读取和解释，不能自己改表、宣布检查通过并提交。下面的任务包保留报表与规则版本，供各责任人核对同一审批对象。

报表审批任务包至少要明确并固定以下要求：

```text
目标：验证锁定报表并生成可审批的异常说明
输入：报表哈希、组织、报表类型、期间、只读数据快照
上下文：口径说明、确定性规则版本、历史对比范围和审批人权限
约束：模型不能修改原表；金额计算和权限判断由确定性规则负责；无具名批准不得提交
成功标准：每个失败项有定位证据，版本变化会使旧审批失效，状态未知不得普通重试
回传：check_results、anomalies、evidence_refs、approval_state、report_hash、rule_version
```

**审批对象必须冻结**

审批人看到的报表与最终入库的报表必须是同一版本。可以保存文件哈希、数据快照 ID 或锁定版本号。审批期间原数据变化时，旧审批应失效并要求重新验证。否则签字对应旧内容，系统执行新内容。

模型生成的异常解释也要与规则结果分开保存。例如“营销费用较上月上升 18%”可以由代码计算；“主要来自市场活动增加”需要来源证据。没有证据时，Agent 应列出待调查问题，不能把相关性写成原因。

**故障演练与指标**

- **旧版本**：同一期间上传新版本后，旧审批进入失效状态；审批记录保留旧哈希、新哈希和差异，不能迁移到新版本。
- **公式异常**：构造“汇总公式通过、明细期间错误”的报表，期间规则必须拒绝放行，并定位出错记录和口径版本。
- **权限越界**：无对应权限的审批人提交决定时，状态保持待审批；审计记录保存主体、报表哈希和拒绝原因。
- **提交超时**：审批接口超时后，动作进入状态未知；系统依据报表期间、审批人和提交 ID 查询真实签字状态，再决定恢复或转人工。
- **重复触发**：相同报表版本再次触发时复用原任务和审批状态，不创建第二条待审批记录；运行日志保存命中的幂等键（用于保证同一业务动作重复请求不会产生重复结果）。

质量指标包括规则覆盖、误报与漏报；版本指标用于检查版本不一致和审批过期的情况；权限指标记录越权尝试；流程指标记录退回次数、审批时延和人工解释所需的时间。任何一类保护指标超过预设阈值，都应暂停放行相应任务，不能因为总体处理速度快就忽略问题。

## 7.15 报表审批的版本锁

上文要求审批对象必须冻结。本节说明怎样在职责划分、版本标识和界面展示上落实这一要求。

**编制、验证、审批和执行分开**

报表编制人负责修正数据；验证流程按规定口径核对公式和计算结果；审批人确认业务解释并承担审批责任；入库或提交则通过专用操作完成。不能让同一个 Agent 同时拥有修改原表、判定正确和正式提交的权限。

**审批对象使用内容指纹**

系统根据报表结构、数据范围和全部数据内容生成版本 ID 或哈希，并将审批记录绑定到该版本。任何单元格、数据源或口径发生变化，审批都会失效，需要重新运行确定性验证。

界面展示新旧版本差异：哪些数字变化、公式是否变化、异常说明怎样修改。审批人不必凭文件名判断 `final-v7-revised` 是否真是最终版。

**Agent 解释异常的边界**

代码计算出“营销费用环比上升 18%”后，Agent 可以从获准读取的预算和活动记录中寻找可能的原因，但只有来源明确的事件才能写入正式说明。若没有证据，就列出待调查的问题，不能写成“主要由于市场活动增加”。

**模拟一次并发修改冲突**

审批人打开报表后，编制人修正一条数据。点击审批按钮时，系统应检测到版本变化，拒绝批准旧页面中的报表，并显示差异。若正式提交成功但响应丢失，应按报表期间和提交 ID 查询结果，不创建第二份正式记录。

月度试运行要覆盖零数据、负数、币种、跨期、公式断链、版本变化和审批人缺席。每类异常都应有明确的状态和后续处理安排，不能只提示“请人工查看”就不再跟进。
