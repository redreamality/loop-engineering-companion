## 10.11 跨循环案例：突然增加的“次日达未到”

一家生活用品网店在周二上午开始收到“页面写次日达，但物流没有更新”的工单。单张工单看起来都是普通物流查询，客服预处理循环按订单查询并起草解释。

到了中午，反馈循环发现同类主题在两小时内超过正常基线。它没有直接宣布物流事故，而是创建调查任务：列出受影响订单、仓库、承运商、下单时间、页面承诺版本和物流轨迹。

**先防止错误继续扩大**

控制面采取四项可逆措施：

1. 控制面将“次日达未到”意图从自动回复降级为人工草稿，同时保留自动分类和事实查询。
2. 知识维护循环暂停引用现有“配送时效”FAQ 的相关答案，并把条目标记为待复核。
3. 营销和商品页循环停止发布未经复核的次日达承诺，同时保留页面版本和地区范围。
4. 系统保留新工单与订单信号，只生成退款候选，不批量承诺退款。

这些措施在根因查明前就可以采取，目的是先阻止可能有误的信息继续传给客户。

**建立事实时间线**

调查时，要读取仓库出库事件、承运商的接收扫描记录，以及客户下单时的页面承诺快照，再按时间梳理事件之间的关系。周一晚，仓库系统把这一批订单记为“已出库”，但该字段只表示内部拣货完成。到了承运商应接收货物的时间，外部物流轨迹仍没有接收扫描记录，因此客服不能把这个内部字段解释为货物已经交接。

客户下单时，页面明确向该地区显示“次日达”，快照保留了这项承诺。因此，客户在未按时收到商品时提出质疑是合理的。随后，仓库记录证实装车故障使实际交接延迟了一天，解释了为什么内部已记为出库，承运商却尚未接收，也将根因确定在交接阶段。

库存扣减情况需要另行核对：相关商品已经从可售量中扣除，商品并未缺货。这个事实可以排除补货不足，却不能证明承运商已经接收。客服回复应说明当前能核实的状态、实际情况与原承诺的差异，以及下一次更新时间，不能用“已出库”字段否定客户反映的情况。

**多条循环各自做什么**

装车故障查明后，逐条安抚客户还不足以阻止错误继续发生：旧 FAQ、页面承诺和通知批次仍可能传播过时信息。表 10-8 按循环分配修复任务，让每一项已确认事实落到相应业务记录，同时保留对外承诺与批量动作的批准要求。

**表 10-8  次日达事故中各循环的应对措施与禁止动作**

| 循环 | 任务 | 不允许做的事 |
|------|------|--------------|
| 工单预处理 | 找到受影响订单，生成一致但个性化的说明草稿 | 自行承诺退款或到达日期 |
| FAQ 更新 | 暂停旧条目，起草“配送状态含义”与异常说明 | 未经知识责任人批准直接发布 |
| 反馈处理 | 整理主题候选与证据供负责人确认，统计范围与趋势 | 把所有物流投诉永久标记到客户身份 |
| 库存巡检 | 确认不是缺货，核对出库与可售状态差异 | 因投诉量直接补货 |
| 内容与页面 | 标记次日达承诺需复核 | 批量修改页面而无地区和生效版本 |
| 主动通知 | 为明确受影响客户建立通知候选 | 联系未受影响客户或重复发送 |

库存巡检确认“不缺货”，就应阻止投诉量被转成补货需求；FAQ 与页面循环则修正“已出库”和次日达承诺的适用说明，不能靠采购解决交接故障。各条循环处理的是同一事故的不同后果，任何一行完成都不能替其他行结案。尤其是个别工单回复与主动通知可能联系同一客户，因此下一步要在发送前核对是否已有等价说明，避免分工之后反而重复联系。

**主动通知的业务键与去重**

客户可能已经通过工单收到单独回复，却又被列入主动通知批次。消息门禁使用“订单 + 事故 ID + 通知类型”作为业务键，并查询同一会话最近发送的内容。已经收到等价说明的客户不再重复接收通知；信息有重要更新时，再在原会话中补充。

批量通知先在十个内部测试订单和五十个低风险真实订单上进行灰度验证，核对收件人、订单、承诺快照、措辞和退订政策，再扩大范围。无法确认发送接口的执行结果时，要查询消息记录，不能重新发送整个批次。

## 10.12 从个别处理到根因关闭

关闭事故前，必须通过以下四项检查。

**客户补救门**由客服负责人把关，需核对受影响订单清单、获批说明、退款或补偿对账结果，以及向客户作出的承诺是否兑现；仍有遗漏订单、状态未知的资金动作或未兑现承诺时，不能关闭事故。

**运营修复门**由仓库和物流负责人把关，需核对交接恢复后的扫描记录、故障原因、在途货物的处置情况和当前服务能力；即使内部字段恢复正常，承运商仍无接收扫描记录时，不能关闭事故。

**事实一致门**由商品、知识和数据负责人共同把关，需核对按地区修订的页面承诺和新 FAQ 版本，确认旧版本引用已经失效、库存状态没有被错误改写；只要还有权威系统继续提供过时信息，就不能关闭事故。

**预防验证门**由循环负责人把关，需核对短窗口告警、主动通知去重回归测试、自动回复的小批量灰度结果、投诉趋势保护指标，以及复盘后新增的测试；保护指标超出阈值时，应重新暂停相关自动化，事故仍保持未关闭状态。

四项检查都通过后，业务问题才算处理完毕。逐个关闭工单只说明这些工单已从待办队列移出；单独修复仓库之后，还要证明对客户的承诺和知识条目已经更新。

**复盘发现的系统缺口**

1. 仓库“已出库”被客服理解为承运商已接收，因此拆成“内部拣货完成”和“承运接收”两个字段；回归样本要求前者存在、后者缺失时回复保持“待交接”。
2. 物流告警只看日总量，因此增加短窗口基线、受影响地区和仓库维度；回归样本要求两小时异常增长触发调查，而普通日波动不触发批量通知。
3. FAQ 没有关联页面承诺版本，因此为条目保存承诺版本和失效条件；回归样本要求页面版本变化后旧 FAQ 自动进入待复核。
4. 主动通知与个别工单没有跨循环去重，因此增加“订单 + 事故 ID + 通知类型”业务键和最近发送查询；回归样本要求已收到等价说明的客户不再收到首轮通知。
5. 自动回复恢复没有灰度步骤，因此增加恢复范围、样本、观察窗口和再次停止阈值；回归样本要求保护指标越界时只暂停相关意图。

每个缺口都需要通过修改字段、规则、测试或运行步骤来补齐；只写一句“注意物流异常”，无法检查措施是否真的生效。

## 10.15 跨循环事件检查表

当客户陈述、系统事实、政策或批准内容相互冲突，且问题已经影响两个以上循环时，由事件负责人填写下面的协同记录。这份记录用于协调处理，不会直接触发执行。业务对象与系统事实从各权威台账读取，暂停动作和去重键由动作服务确认，对外说明与补偿任务分别由沟通批准人和补偿负责人填写，恢复灰度与停止条件由循环负责人确认。


关闭事件前，至少要确认各权威系统记录的事实已经一致、受影响对象和冻结范围可追溯、旧动作不会重复执行、对外说明对应当前有效的批准，同时明确补偿负责人，以及恢复运行和再次停止的条件。任一项未落实，事件都应保持未关闭状态，相关自动动作继续暂停。缺失的事实交由相应责任人核对；动作状态未知时，应先查询外部账本，不得直接重试。
