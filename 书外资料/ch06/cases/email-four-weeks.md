# 邮件循环的四周落地案例（完整版）

> 《循环工程》配套资料（ch06 业务场景循环）。来源：原第 7 章 7.9 节；新版 6.2 保留压缩版，分类结果 JSON 示例与修复五条全文在此保留。章节引用已按新版章号改写。


一家十五人的设计咨询团队每天收到约一百二十封邮件，其中系统通知、供应商、客户项目和营销内容混在一起。运营负责人唐宁每天上午花四十分钟整理自己的收件箱，下午还会漏看一两封需要当天处理的客户邮件。

团队把目标限定为：整理唐宁的一个工作文件夹，生成个人摘要和回复草稿，不自动删除、归档或发送。客户资料只读取当前会话和对应客户关系管理系统（Customer Relationship Management，CRM）摘要；CRM 是权威客户台账，不是从邮件推断的标签。

**第 1 周：观察发现层**

系统用事件通知记录新邮件，同时每天下午做一次补偿扫描。它不调用模型，只建立候选任务。团队发现：

- 同一会话的回复会产生多个消息事件，因此发现层必须按会话 ID 合并事件，避免同一会话产生多个任务。
- 日历邀请与普通邮件需要不同处理；如果共用同一分类规则，邀请可能被误当成待回复邮件，团队因此将处理类型纳入任务身份。
- 一些转发邮件的 `From`（发件人字段）是同事，真正发件人在正文中；系统需要保留原始正文并把身份不确定项送人工确认。
- 邮件规则已经把部分客户邮件移到子文件夹，扫描范围最初没有覆盖；补偿扫描随后扩展到授权文件夹集合并记录覆盖差异。
- 退订和垃圾邮件不适合进入语义分类，所以固定规则先将它们排除，并把排除数量纳入覆盖核对。

因此，任务身份采用邮箱账号、会话 ID 和处理类型，规则版本绑定在任务上；固定规则先排除退订、已确认的垃圾邮件和系统健康通知；事件负责快速发现，扫描按“收到时间 + 稳定邮件 ID”补漏。

第一周只将候选会话与人工实际处理清单作比较。覆盖率稳定后，才开始调用 Agent。这样，后续出现质量问题时，就能区分问题出在“邮件没进来”，还是“进来后分错了”。

**第 2 周：分类与摘要**

第二周开始调用 Agent 分类和生成摘要。下面是 Agent 对一个客户会话返回的结果示例：

```json
{
  "category": "需要今天处理",
  "summary": "客户询问周三评审是否仍按计划，并担心上次反馈未处理",
  "deadline": "2026-08-14T17:00:00+10:00",
  "suggested_action": "核对项目计划后起草回复",
  "evidence": ["msg-1082:p2", "msg-1076:p4"],
  "risk_flags": ["client_commitment"]
}
```

只有原文明确说明了截止时间，才在 `deadline` 字段填写。如果模型根据“能否尽快回复”推断出具体时刻，事实验证应拒绝这一结果，改为标记“无明确截止时间”。

团队为分类界面增加四个快捷操作：确认、修改分类、标记遗漏风险、不是工作任务。每次修改要求选择原因，不要求写长说明。到首月复盘时，这些原因记录显示，大部分分类修改来自三种情况：会议邀请、供应商对账和客户在旧主题中提出新问题。团队针对这些情况分别建立专门规则，或允许在同一会话下创建其他类型的任务。

**第 3 周：起草与审批**

只有归为“需要今天处理”、且不涉及合同、退款、投诉或安全风险的邮件，才进入起草流程。任务包提供当前会话、获准读取的客户摘要和项目状态，只允许创建草稿。

审批界面分成四块，让审批人按证据顺序检查草稿：

**原始请求**：展示客户原文中的问题和时间引用，审批人据此判断草稿有没有遗漏请求或误解时限。

**已核实事实**：展示项目系统读取的日期、负责人和当前状态，审批人据此确认草稿中的事实来自当前权威记录。

**风险与缺失**：列出未确认承诺、冲突资料和需要人决定的事项，审批人据此决定退回、补资料或继续起草。

**拟发送草稿**：展示草稿与已获批准的模板有何差异，同时列出收件人和附件，供审批人确认对外承诺及信息发送范围。

唐宁可以修改草稿。点击批准后，系统仍要再次核对收件人、项目日期，以及会话是否新增了邮件；批准绑定的是当前内容与证据，审批期间若客户补发邮件，旧草稿进入 `stale`，不能发送。

**第 4 周：处理一次严重漏报**

一封邮件写道：“如果这次仍无法按约交付，我们将让采购重新评估合作。”Agent 把它当作普通项目进度邮件处理，没有标记客户关系风险。唐宁在审批时发现了问题，因此没有向外发送错误回复。

团队没有直接写一条固定规则，把出现这句话的邮件一律归为“投诉”。复盘发现，原有验证主要关注退款、合同和明确的负面词语，缺少“终止、重新评估供应商、升级给管理层”等客户关系风险样本。修复包括：

1. 将该邮件和相似的真实邮件加入高风险评测，用这些样本反复检验系统能否识别合作关系可能终止的信号。
2. 让风险评审重新读取原文而不只看分类摘要，避免摘要遗漏条件导致风险降级。
3. 将涉及合作关系终止的邮件一律转交人工处理，并禁止自动发送；在积累足够的人工审核通过记录之前，不考虑开放自动发送。
4. 在观察期内提高该类邮件的抽样比例，检查漏报是否减少，而不是只看平均准确率。
5. 记录规则版本并重新评测过去四周样本，确认修复没有改变其他类别的覆盖和误报。

这次事件展示了人工门禁的作用，也说明“没有发错”不代表系统无需改进。近失事件是指错误已经出现、但被门禁拦住而没有影响客户的事件；险些漏过的高风险邮件要按近失事件处理，第 8 章会专门讨论。
