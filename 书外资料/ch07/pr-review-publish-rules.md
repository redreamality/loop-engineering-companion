# PR 评审循环的发布规则（完整版）

> 来源：《循环工程》原第 11 章 11.17，2026-11-07 缩编改写时外移；压缩版见新第 7 章 7.6。

自动评审容易产生大量无用评论。即使模型列出十个“可能的问题”，发布器也只应公开证据充分、可复现且与当前提交相关的问题，其余保留在内部报告或待核实列表中。证据充分、会阻止合并的问题，可以作为正式评审意见；不确定的判断以询问的方式提出；已有格式化工具处理的风格问题，不再发表评论。

## 评论发布四条件

每条问题报告发布前，都要满足四个条件：

1. **版本仍然有效**：评论绑定的提交和代码行仍然存在；
2. **证据充分**：能指出违反的需求、可复现路径、静态规则或具体后果；
3. **能够据此处理**：作者知道需要修什么或需要回答什么；
4. **不重复**：CI、其他评论或本次评审中针对同一根因的意见尚未指出该问题。

评论发布也需要幂等键，例如 `pr + head_commit + finding_fingerprint`，评审政策版本（`reviewer_policy`）作为绑定参数记录；政策变化后确需重新发布的评论，按新政策版本另记一条发布记录。作者推送新提交后，旧评论可以保留历史，但状态要显示它基于旧版本；评审机器人也不能在新代码行上重复发布同一内容。

## 作者不同意时怎么办

作者可以把评论标记为“不适用”“风险已接受”“已修复”或“待讨论”，并附上理由。循环将处理结果交给规则负责人分析：误报集中出现，说明评测或上下文可能有缺失；接受风险的决定必须符合仓库的权限规定；同一类已确认的问题反复出现时，规则负责人可以增加静态规则、模板或测试，让系统更早发现和阻止这类问题。

作者提出异议后，Agent 不应自行追加论据、连续留言试图说服对方。系统应把争议交给代码所有者，并停止自动回复。

## 合并前重新核对

评审通过只对特定提交有效。合并前，应按保护规则确认所需检查和批准是否齐全、是否已与目标分支的最新状态同步，以及是否还有未解决的讨论。若 PR 在批准后增加提交，高风险仓库要求重新批准。自动评审结果可以作为判断依据，但系统不能因为自己“未发现问题”，就使用管理员权限绕过保护规则。
