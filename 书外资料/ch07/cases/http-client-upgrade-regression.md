# 案例：HTTP 客户端升级在测试全绿后的回归（完整复盘）

> 来源：《循环工程》原第 11 章 11.11，2026-11-07 缩编改写时外移；正文压缩版见新第 7 章 7.8。

以下版本号、流量比例和指标均为演示数据，不代表某个实际库或平台。某 Node.js 服务每周扫描依赖的小版本更新。一个 HTTP 客户端库从 4.2.1 升到 4.3.0，官方变更说明没有标注破坏性变更。Agent 更新锁文件，单元测试、类型检查和构建全部通过，PR 由代码所有者批准并合并。

发布到 10% 流量后，服务超时率上升。升级版本改变了默认连接复用行为，现有测试使用本地模拟服务器，没有覆盖生产代理与长连接。部署事件把版本、提交、依赖任务 ID 和流量批次关联，观察层比较升级前后同一服务的错误率、超时、连接数和业务成功率；指标越过预设阈值后，部署熔断，依赖任务进入“需要回滚”状态。回滚由部署控制面使用已批准的旧构建产物执行。调查任务固定失败版本和环境，增加一个经生产代理的集成测试；Agent 对照官方变更说明与实际配置，发现新版本需要显式设置连接策略。团队在“等待上游修复 / 显式配置旧行为 / 接受新行为并调整代理与容量”中选择方案二，在同一升级任务下改用新策略版本重新运行，旧失败的运行记录保留。

## 这次失败可以怎样改进后续循环

- **依赖位置改变风险判断**：4.3.0 的连接复用变化影响生产请求路径，证明“小版本”不等于低风险。规则负责人可以把“位于网络请求路径”加入该依赖类型的风险分类，不能把所有小版本升级一律标成高风险。
- **测试环境没有覆盖生产网络的实际行为**：原单元测试只使用本地模拟服务器，没有覆盖生产代理与长连接。测试负责人可以为同类网络依赖增加代理集成测试要求，但不能因为一次回归，就认定所有依赖都需要同一环境。
- **发布观察需要关联到具体变更**：金丝雀指标绑定依赖任务 ID、提交和流量批次后，团队才能判断超时上升是否与本次升级有关。部署规则可以要求此类任务保存变更标识，不能只看服务总体指标，不关联具体版本。
- **回滚应使用已验证产物**：事故中使用已批准的旧构建产物恢复了服务，没有临时生成新补丁。回滚计划可以要求保存上一个已验证的产物及其部署证据，不能把“现场修复”写成默认恢复策略。
- **失败经验先形成候选规则**：本次失败为“网络依赖升级增加代理集成测试”这一候选规则提供了依据。规则负责人仍要用其他样本评测覆盖范围和成本，批准后才能更新升级策略；不能依据单次事故直接制定全局政策。
