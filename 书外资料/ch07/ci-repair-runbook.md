# CI 修复循环接入仓库：基本运行手册

> 来源：《循环工程》原第 11 章 11.16，2026-11-07 缩编改写时外移；要点已并入新第 7 章 7.3。

把修复循环从演示接入正式研发流程时，至少要安排好事件接入、任务标识、工作区隔离、凭证管理、结果回传和清理。下面是一份不依赖具体工具的基本运行手册。

## 事件入口

CI 平台只把已完成且失败的作业事件交给发现层。发现层先验证事件签名（用于确认通知确由 CI 平台发出），再读取仓库、提交、工作流、作业、重跑编号和目标分支。业务任务 ID 可以写成下面的示意式；它不是可直接执行的命令，实际系统还要定义字段编码、版本化和冲突处理：

```text
repo + head_commit + workflow + job
```

同一作业重跑不会创建第二个修复任务，只增加一次运行；提交变化则创建新任务，并把旧任务标为基线过期。修复策略版本（`repair_policy_version`）绑定在任务上，不写进任务 ID：策略升级时在同一任务下用新版本重新运行并记录版本变化。处理来自 fork 的提交时，使用无写权限的令牌，不能沿用主仓库的密钥等机密凭证。

发现层还要排除不适合自动修复的情况：作业取消、运行器容量不足、凭证过期、第三方服务中断和组织配额耗尽。遇到这些情况，应创建运行事件或发出通知，不应让编码 Agent 猜测如何修改代码。

## 隔离与凭证

每项任务从固定提交创建新工作树、容器或远程沙箱。环境只获得读取仓库和回传产物所需的最低权限。创建分支或 PR 的服务身份与执行测试的身份分开；合并和部署不交给修复 Agent。

依赖下载若需要令牌，令牌只允许读取指定包注册表，具有短有效期，不写入提示、日志和补丁。任务结束后销毁工作区前，控制面先保存允许保留的差异、命令证据和测试结果。清理失败本身要告警，因为遗留工作区可能包含代码和临时凭证。

## 复现门槛

开始修复时，必须先在同一提交上复现目标失败。若本地环境不能复现，系统应先比较运行镜像、语言版本、锁文件、环境变量名和命令；环境差异尚未解决前，不扩大原定修改范围。复现证据包括实际命令、工作目录、退出码和失败指纹。

失败指纹用于判断有没有进展，但不能只取日志的最后一行。类型错误的指纹可以包含规则、文件、符号和位置；测试失败的指纹包含测试标识、断言和相关异常；构建失败的指纹包含阶段与工具版本。应用补丁后，如果只是错误位置变了，根因仍然相同，就不能算作取得了新进展。

## 交付 PR

通过验证后，由控制面决定能否创建 PR，不能仅凭 Agent 的文字报告放行。PR 描述模板见 [templates/ci-repair-pr-description.md](templates/ci-repair-pr-description.md)。

推送前再次读取目标分支和 PR 状态。若同一问题已有尚未关闭的 PR，就更新相关证据，或将当前任务标记为重复并结束，不再创建第二条修复分支。若基线已落后，补丁又无法无冲突地应用到新基线上，系统应先由发现层按新提交更新基线，再创建新的运行，不让 Agent 随意解决与任务无关的冲突。
