## 一、事实与案例口径

书中内容分为四类，分别是本书方法、可核查事实、工程建议和教学案例。区分这四类，是为了说明每一条结论的可靠程度和适用边界：读者据此判断某项说法应当被直接采纳、查证后采纳，还是仅作为讨论起点。

**本书方法**包括四层能力模型、发现—交付—验证—记忆—调度五步公式、六类基础设施、任务包、状态、门禁和成熟度。它们是用于分析和搭建循环的工作地图，不是国际标准或行业公认的唯一分类。

**可核查事实**包括术语使用、产品能力、标准条文和官方工程经验。相关判断以原始来源文本、产品官方文档、标准和公共机构资料为依据，并保留日期、适用范围和限制。

**工程建议**包括状态命名、任务身份、验证阶梯、业务幂等、预算分层、无进展检测、事故演练和退役流程。它们综合了分布式系统、工作流和 Agent 实践，用于设计讨论，不代表某个标准逐字要求。

**教学案例**中的公司、人物、业务对象、金额、比例、日期和事故数据，除非正文明确给出来源，均为教学用虚构或合成信息。案例用来展示状态、责任和决策，不是行业统计，也不证明使用 Agent 必然获得相同结果。

本书不构成法律、财务、医疗、安全或合规意见。资金、身份、员工、健康、法律承诺、隐私和受监管业务应由具备相应职责与专业资格的人结合所在地区和行业要求决定。

公开可访问不等于可以转载、改编或用于商业发布。来源页面只作为事实核查入口，本书不复制长段落、截图或页面图像；引用、商标和许可证仍须按来源站点条款和适用法律逐项复核。无法确认许可范围时，只保留事实摘要和链接，不把"开放访问"写成"已获转载许可"。

### Floatboat 使用示例的适用范围

第 5 章和第 6 章分别以 Floatboat 的定时任务，以及 Combo Skill 使用、工作台制作和自用 Combo 制作为实践对象；第 8 章补充了将固定步骤整理为 Workflow 的成本优化方法。相关能力的依据截至 **2026 年 9 月 30 日**，来自产品实现与开发文档的核对，以及作者补充的对话式使用方式；这些依据不构成所有发行版本、账号和设备都支持同一路径的保证，也不代表书中业务练习已经完成实机验收。

四组依据分别记为 `SRC-FB-001`、`SRC-FB-002`、`SRC-FB-003`、`SRC-FB-004`。工作台模板的仓库入口见下文 `SRC-FB-003`；其余依据尚未在本书中提供完整的公开检索入口，不能用其他产品的文档或一份能力宣传清单代替。操作前应取得相应功能、匹配的版本说明及必要资料；未取得工作台模板或没有相应功能入口时，不把普通文件夹或一段聊天请求当作已经创建的产品对象。

`SRC-FB-001` 核对的是 Automation 的任务保存、日程与运行生命周期，以及另一条独立的 Workflow 触发绑定路径。两条路径不是同一种对象；立即运行会触发实际执行，不是无副作用的演示。业务去重、失败重试策略、费用上限和设备离线后的补跑，需要分别确认，不能从定时功能推出。

`SRC-FB-002` 核对的是 Combo 安装、会话绑定与激活，以及草稿初始化、打开、状态查看和提交。提交检查包只检查结构和身份，业务结果是否正确由业务验证确认；依赖就绪和实际调用仍需检查。普通 Skill 导入、制作自用 Combo 和向市场提交发布是不同过程，书中的教学包名称对应自用练习，市场上是否有同名产品需要另行查证。

`SRC-FB-003` 对应的工作台模板为 **`floatboatai/floatboat-workbench-template`**，仓库地址：<https://github.com/floatboatai/floatboat-workbench-template>。核对范围包括本地初始化、检查、预览、SQLite 存储和打包，以及开发文档中的客户端连接与导入说明。读者应从该仓库取得模板，记录提交号或发布版本，并按该版本的说明核对环境和命令；访问受限时先确认账号权限或取得授权副本。仓库地址用于定位模板，各版本与书中命令是否一致需要按该版本核对。桌面导入、账号授权及外部服务连接仍需在实际客户端验收。创建工程只提供开发基础，页面、字段、业务规则和权限仍需制作；本地预览成功后，桌面接入仍要单独验证。

`SRC-FB-004` 核对的是 Workflow 由宿主直接执行、仅在流程显式调用 Agent 时进入模型处理的边界。依据包括《Floatboat Workflow 功能手册》、Workflow Context 的 Agent 调用实现，以及作者提供的"帮我创建一个workflow，作用是：xxx""把当前对话整理成combo/workflow"等自然语言用法；后者是自然语言示例，实际使用要按产品文档确认语法，一键转换成功需要单独验证。"不消耗模型 token"只指不调用模型的固定执行部分，创建与修改的对话、流程内模型步骤会消耗 token，第三方服务、资源或付费流程按各自的计费规则另行计算。

使用时要分清功能入口与工作结果：查到运行记录后，还要确认业务结果是否已正确交付；打开页面后，还要确认数据是否已正确保存；提供确认入口后，还要确认外部动作是否具备版本绑定审批。书中的样本、预期输出、处理数量和时间均为教学安排，不是产品默认值或真实运行记录。判断一次运行是否完成时，应依次检查五项：任务是否以正常完成状态结束，所需资料是否齐备，输入是否重复，运行过程是否被人工停止，以及中断后是否能够恢复并重新执行。这五项既适用于产品内置的运行记录，也适用于自建的循环，任一项不满足时，本次运行都只能记为未通过验收。

## 二、术语归因

本节说明书中几个核心术语的公开来源与流传顺序，目的是明确它们的使用边界，而不是裁定谁最早提出某个概念。凡是只能追溯到二手转述的说法，本节都注明其证据不足。

**Loop Engineering**

Addy Osmani 于 2026 年 6 月 7 日在个人网站发表 *Loop Engineering*，系统化阐述"设计一个反复提示和驱动 Agent 的系统"的做法，使"Loop Engineering"这一叫法得到公开传播；这不构成 Google 官方发布，也不足以证明 Osmani 首创了所有循环思想。该文引用了当时其他 Agent 工具作者和工程负责人的类似表述，说明相关实践已有更广的讨论。

Osmani 在发文时的个人简介称自己曾在 Google 工作十四年以上，最近担任 Google Cloud AI Director。正文因此使用"前 Google 工程负责人"等历史身份，避免把个人文章变成其前雇主立场。

来源：

- Addy Osmani, *Loop Engineering*, 2026-06-07：<https://addyosmani.com/blog/loop-engineering/>
- Peter Steinberger 关于"designing loops that prompt your agents"的公开帖：<https://x.com/steipete/status/2063697162748260627>

Osmani 文中还转述了 Claude Code 负责人 Boris Cherny 关于"写循环"的说法，但该二手转述缺少可独立核验的原文。因此，它不属于可核验的逐字引语，也不足以判断谁最早提出循环思想。

**Prompt Engineering**

GPT-3 论文在 2020 年系统展示了仅通过自然语言任务描述和少量示例，让通用语言模型适配多种任务的方式。这是后来提示词实践的重要技术背景，但不能据此断言 OpenAI 发明了"prompt engineering"这个词。公开资料也没有形成无争议的唯一首创者结论。

- Tom B. Brown et al., *Language Models are Few-Shot Learners*, 2020：<https://arxiv.org/abs/2005.14165>

**Context Engineering**

2025 年 6 月，Shopify CEO Tobi Lütke 用"context engineering"强调为模型提供足以解决任务的上下文；Andrej Karpathy 随后进一步将任务说明、示例、检索数据、工具、状态、历史和压缩策略纳入这一说法。这些公开表述支持"显著推广"的判断，但不足以证明他们发明了该术语。

- Tobi Lütke 原帖：<https://x.com/tobi/status/1935533422589399127>
- Andrej Karpathy 原帖：<https://x.com/karpathy/status/1937902205765607626>

**Harness Engineering**

2026 年春，Viv Trivedy 用"Agent = Model + Harness"描述模型之外的工作系统。Osmani 在 2026 年 4 月的文章中把"harness engineering"的命名归功于 Trivedy，并把提示、工具、上下文政策、钩子、沙箱、子 Agent、反馈、恢复和可观测性等纳入 harness。

- Viv Trivedy, *The Anatomy of an Agent Harness*：<https://x.com/Vtrivedy10/article/2031408954517971368>

Trivedy 长文页面没有可独立核验的精确日期，因此采用"2026 年春"这一保守口径；若需要精确到日，应以页面存档或原作者公开确认的日期为准。

**本书的四层模型**

提示词、上下文、执行环境和循环来自不同作者、时期和实践语境。没有一份所列标准宣布它们构成严格递进的四阶段历史。本书把它们组织成四层，用来判断一项问题究竟缺一句清楚指令、缺背景、缺可控执行环境，还是缺持续任务系统。

## 五、幂等、重试与批任务控制

RFC 9110 第 9.2.2 节定义 HTTP 方法的幂等语义：多次相同请求对服务器产生的预期效果与一次相同。标准允许客户端在通信失败后自动重试幂等请求，并提醒非幂等请求只有在客户端知道其语义实际幂等或原请求未被应用时才可自动重试。

- IETF, *RFC 9110: HTTP Semantics*, §9.2.2：<https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2>

这一原则也适用于业务动作：邮件、付款、退款、工单和发布需要稳定业务键、状态查询或条件写入。本书把这一点作为工程归纳提出，并非某份标准逐字要求。HTTP 的 DELETE 在协议语义上幂等，不代表删除可撤销或低风险；POST 也不代表永远不能重试，应用可以用业务幂等协议使其安全。

Kubernetes Job 文档展示了成熟批任务中的两类上限：失败重试次数和总运行时间，并允许按失败原因决定是否重试。这里借用的是"同时限制次数与总时限、区分瞬时与永久失败"这一控制模式；Kubernetes 本身不是面向 AI Agent 的专用标准。

- Kubernetes, *Jobs*：<https://kubernetes.io/docs/concepts/workloads/controllers/job/>

指数退避与抖动属于成熟分布式系统常见做法。本书不引用具体参数；部署时应结合实际服务的官方文档和错误语义设置上限，并区分可重试错误与不可重试错误。相关参考：

- AWS, *Timeouts, retries and backoff with jitter*：<https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/>
- AWS, *Making retries safe with idempotent APIs*：<https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/>
