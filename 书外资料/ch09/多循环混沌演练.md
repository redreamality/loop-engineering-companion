# 多循环混沌演练

> 来源：原第14章 14.17 节。对应正文第9章 9.7 节（连接的故障恢复）。

单项恢复检查通过后，还要确认故障叠加时保护不会互相失效。例如，审批期间事实更新，同时消息通道限流，系统既要使旧批准失效，也要限制重试，不能为了清空积压跳过任何一项。下表在非生产环境或影子运行中检验这些组合，每次注入前都要写清预期状态、保护指标、停止条件和恢复证据。

表 1  多循环混沌演练的注入与恢复证据

| 故障注入 | 期望状态与保护指标 | 停止条件 | 恢复证据 |
|----------|--------------------|----------|----------|
| 上游事件重复并乱序 | 消费者按对象和版本去重，任务数不增加，状态不倒退 | 出现第二项有效任务或旧版本覆盖新版本 | 重放记录与任务台账一一对应，当前版本保持最新 |
| 审批期间权威数据更新 | 旧批准失效，任务回到待验证；外部动作数为 0 | 旧内容进入动作队列或批准仍显示有效 | 新版本重新验证并由批准人确认，旧哈希不可执行 |
| 外部 API 限流 | 相关调用退避或熔断，高风险任务保留容量 | 重试预算耗尽、限流扩散或请求持续增长 | 探测请求连续通过，积压按当前事实小流量释放 |
| 人工审批容量减半 | 上游降速，最老等待可见，低风险批量不挤占高风险决定 | 超时任务无负责人，或批准时间异常缩短 | 替班与限流生效，抽查批准质量未下降 |
| 低优先级循环产生十倍任务 | 该循环背压，其他任务的最低服务份额保持 | 共享资源或人工队列被单一循环占满 | 峰值任务已合并或过期，正常队列恢复且无饥饿 |
| 动作已成功但响应丢失 | 任务进入"动作状态未知"，按原幂等键查询 | 出现第二次动作请求或新幂等键 | 账本与外部系统只有一次动作，任务关联原结果 |
| 依赖循环暂停 | 下游进入带截止和负责人的明确等待，不自行绕过 | 下游猜测结果、静默完成或无限等待 | 依赖恢复后按当前版本重验，等待任务逐项释放 |
| 全局预算接近硬上限 | 非关键模型 Token 消耗停止，高风险验证保留 | 超出硬预算或为省费关闭严重错误验证 | 预算预测回到安全区，异常路由关闭，单位任务成本恢复 |

表 1 的停止条件限定演练可以继续到哪里，恢复证据则说明修复后凭什么重新放行，两者不能互换。旧批准仍显示有效时，即使外部动作尚未发生，也已达到对应停止条件；响应丢失后能正常调用接口，也不等于可以重发，仍须证明账本与外部系统只有一次动作。若发现高风险副作用或证据链断裂，应立即停止，不能为了完成整套演练继续扩大影响。

通过演练需要保存实际的状态、版本和动作记录，不能只听搭建者解释"系统会处理"。表中的故障覆盖当前声明的连接与保护，不保证未来新增连接也成立。所得证据要进入连接评审（见本目录《连接评审卡.md》），缺少恢复依据的连接继续保持人工交接或影子运行。

混沌演练不需要破坏真实业务，可以使用影子任务、测试租户和模拟动作服务。重点是验证控制面怎样应对组合故障；每个组件单独通过测试，并不能证明组合后的系统仍然稳定。
