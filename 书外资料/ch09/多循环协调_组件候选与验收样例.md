# 多循环协调：组件候选与验收样例

> 来源：原第14章 14.11 节三级小节"按协调要求选择可替换的组件"。对应正文第9章 9.7 节。

前面的退款流程既要长时间等审批，又要在付款响应丢失后查询结果；项目日期变更则要把同一版本可靠地交给多个消费者。这些要求分别涉及流程状态、事件投递、权威记录和追踪，不能仅凭某个组件支持"工作流"就认为问题已经解决。下表先划分责任，再列出可选实现，以及更换实现时应保留的业务接口。

表 1  多循环协调责任与候选组件映射

| 责任 | 可选实现 | 适合优先验证的场景 | 保持可替换的边界 |
|------|----------|--------------------|------------------|
| 长流程、等待与补偿 | Temporal、Prefect 或 Dagster | Temporal 可先用于跨服务、长时间等待和补偿较多的业务流程；Prefect 可先用于 Python 任务流；Dagster 可先用于围绕数据资产、分区和物化关系的流程 | 业务状态和幂等键保存在领域对象中，工作流只调用 `start`、`signal`、`cancel`、`query` 这类适配接口 |
| 事件投递与背压 | Kafka、Redis Streams 或 RabbitMQ | Kafka 适合先验证日志保留、重放和多消费者；已有 Redis 的小规模系统可先验证 Redis Streams；RabbitMQ 适合先验证队列路由、确认和死信处理 | 事件模式定义、业务对象 ID、版本和去重规则独立于 topic、stream 或 queue 名称 |
| 权威状态与事务边界 | PostgreSQL 或组织已有的事务数据库 | 需要同时提交业务状态和待发布事件时，用事务外发箱（outbox）记录先证明不会出现"状态已改、通知丢失" | 仓储接口暴露版本检查、状态迁移和 `outbox` 接口，不让循环直接依赖某一套 SQL 扩展 |
| 跨循环追踪 | OpenTelemetry 配合 Jaeger，或兼容 OpenTelemetry 的其他后端 | 先验证 `task_id`、`run_id`、业务对象 ID 和事件版本能否跨进程传播；Jaeger 可作为查询 trace 的一种后端 | 埋点使用 OpenTelemetry API 和约定字段，查询后端可以更换 |

表中产品只能完成部分技术工作，任务状态、业务语义和幂等边界仍要在领域对象与适配接口中定义。选型时，正常演示能跑通还不足以作出决定：Temporal、Prefect、Dagster、Kafka、Redis Streams 与 RabbitMQ 在表中都只是待验证的候选，官方入口见来源说明 `SRC-PLAT-002`；OpenTelemetry 与 Jaeger 的入口见 `SRC-PLAT-004`。PostgreSQL 只作为常见事务数据库的示例；事务外发箱是通用设计做法，不依赖某个产品的专有能力。先写清本系统必须遵守的业务规则，再针对实际使用的版本和部署方式，验证等待、补偿、保留、确认与重放，比较哪种实现更便于处理故障。如果团队已有能够满足这些要求的队列、数据库或追踪平台，通常不必仅仅为了换用某个产品而迁移。

**用同一组故障样本做选型（P-42 固定验收步骤）**

把正文 9.1 节的项目 P-42 作为固定验收样例，让每套候选实现处理同样的业务身份、版本 18 到 19 的状态变化和三项下游任务。验收按下面的顺序进行：

1. 先跑正常路径，确认三条循环只读取同一个权威业务对象，没有各自复制承诺日期；
2. 在 PostgreSQL 提交版本 19 后、发布事件前终止后台投递进程，重启后检查事务外发箱能否继续投递；
3. 重复发送版本 19，再晚到一条版本 18，确认消费者不会重复建任务，也不会把状态退回旧版本；
4. 让消息系统短暂不可用，确认外部沟通保持暂停，积压恢复时按当前状态重验，不原样重放；
5. 在动作服务执行后丢弃响应，确认重试会按业务幂等键查询既有结果，不发送第二次；
6. 从任一业务对象打开追踪记录（trace），检查是否能关联工作流运行、事件投递、状态版本、验证和最终动作。

记录每种实现需要多少业务补偿代码、有哪些人工恢复步骤、哪些等待要求无法表达，以及迁移成本。比较时，要看团队能否解释故障原因并完成恢复，而不只是看产品功能表有多长。通过验收后，再决定保留当前组件、更换适配器，还是只在少数长流程中引入工作流引擎。
