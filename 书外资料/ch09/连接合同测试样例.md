# 连接合同测试样例

> 来源：原第14章 14.20 节。对应正文第9章 9.7 节。

循环之间的事件和状态是生产接口。它们需要像 API 一样有示例、版本、兼容规则和消费者测试。一份事件合同可以写成：

```text
事件：project.milestone.changed.v2
生产者：项目事实服务
业务身份：project_id + milestone_id + version
必填字段：旧日期、新日期、状态、变更原因、批准 ID、发生时间
顺序：同一里程碑版本单调递增；跨里程碑不保证顺序
重复：消费者必须幂等
撤回：发布 milestone.change.reverted，不删除历史事件
敏感字段：不包含客户联系人和合同正文
保留：示例保留期为事件 90 天，权威事实长期保留；实际期限按组织政策和合规要求确定
已知消费者：客户承诺、周报、内容排期、资源计划
```

生产者需要测试模式定义和业务约束，消费者则要测试遇到重复、乱序、字段缺失、新增字段和撤回事件时能否正确处理。契约仓库应保存每个消费者当前支持的版本。这样，生产者准备删除字段前，就能查出哪些循环仍依赖这个字段，不必临时到群里询问。

语义兼容往往比格式兼容更难。例如，字段仍叫 `completed`，含义却从"内部处理结束"改成了"客户已确认完成"。JSON 格式虽然完全兼容，业务含义却已经不同。因此，连接变更说明要写清字段语义、时间口径、空值含义，以及该字段是否可作为权威依据。影子运行既要比较解析结果，也要检查下游任务数量、路由和动作是否发生变化。

消费者遇到未知状态时，不能默认按最接近的旧状态处理。涉及外部承诺或资金的任务，应进入明确的等待状态；低风险报表可以显示"未知"，同时发出告警。不能为了让流程继续，就把未知状态解释成已完成。
