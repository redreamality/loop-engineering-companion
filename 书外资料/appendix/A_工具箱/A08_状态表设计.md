# A.8 状态表设计

> 原附录 A A.8 节外移；文中章号已按新版调整。

先列业务上需要区分的状态，再选择技术实现。状态表示业务事实，不是界面颜色或模型信心分数。下面用一项需要人工批准、且动作响应丢失的任务说明这些状态：

以下箭头只表示这条异常路径，不是所有任务必须依次经过的状态，也不是可直接执行的程序。任务由 `candidate`（已发现但未满足运行条件）进入 `ready`（前置条件齐全），再进入 `running`、`verification` 和人工决定；`approved` 只表示具名角色批准具体版本，外部动作此时尚未完成。`action_pending` 表示动作请求已排队，本例因响应丢失进入 `action_status_unknown`，经查询确认动作已执行且业务完成证据齐全，才进入 `completed`。

```text
candidate
→ ready
→ running
→ verification
→ waiting_for_human
→ approved
→ action_pending
→ action_status_unknown
→ completed
```

正常收到确认且满足业务完成条件时，可以从 `action_pending` 直接进入 `completed`。未知后的查询也有不同结果：确认已执行，就关联回执并核对完成条件；确认未执行，要重新核对授权、数据有效期和预算，再按策略决定是否重试；仍无法确认，就保留未知状态并转人工。查询请求返回答案后，还要核对业务完成条件才能判定任务完成。

旁路状态包括：

```text
duplicate
out_of_scope
needs_source
blocked_by_dependency
baseline_stale
retry_scheduled
paused
cancelled
failed_permanent
handed_to_human
```

旁路状态不是失败的同义词：`duplicate`、`out_of_scope` 和 `needs_source` 应说明是否终止当前任务并转交；`retry_scheduled`、`paused` 和 `blocked_by_dependency` 应说明恢复入口；`failed_permanent`、`cancelled` 和 `handed_to_human` 应保存终止或接手证据。仅有这些名称，还不能让接手者决定下一步。前例进入 `action_status_unknown` 后，谁去查询、查询期间能做什么、多久没有答案就转交，都需要写进状态约定。下面的状态模板用于逐状态填写：

| 字段 | 要回答的问题 |
|------|--------------|
| 进入条件 | 什么证据允许进入 |
| 所有者 | 谁或哪个系统负责下一步 |
| 允许动作 | 该状态下可以读写什么 |
| 等待对象 | 等谁、等哪个版本或外部状态 |
| 截止 | 何时提醒、升级、取消或降级 |
| 离开条件 | 哪个事件或决定推进 |
| 过期 | 哪些事实变化会让结果失效 |
| 观察 | 需要哪些日志和指标 |

对 `action_status_unknown`，进入条件应指向已发出的请求和丢失的响应，允许动作应限定为查询、核对与必要转交，不能包含普通重试。所有者承担查询责任，等待对象则是可确认外部结果的证据；只填一个负责人姓名而不写等待什么，接手者仍无法判断何时结束调查。离开条件必须对应前述三种查询结果，超过截止也只能触发提醒或升级，不能自动把"未知"改成"未执行"。

"过期"与"观察"进一步限制恢复。调查期间若批准版本或权威事实已变，即使确认原动作未执行，也要重新核对执行条件；日志和指标则要让接手者看见查询是否持续无结果，因此应填写名称、统计窗口和触发阈值。这些字段按状态分别定义，不要求每项任务走同一条路径。权限拒绝、输入无效、验证退回与动作未知的恢复依据不同，用一个 `failed` 合并后就无法据此选择处置。下一节的动作请求需要携带查询标识，正是为了让这里的等待和离开条件有证据可查。
