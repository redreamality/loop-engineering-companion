# 每日待办试运行的数据字段与用途

> 编号说明：本文件由原第 6 章外移，保留原稿表号与小节号（表 6-x 对应新版正文表 5-x；6.x 对应新版 5.x）。

原任务清单只有标题、完成状态和截止日期，足以供熟悉情况的人浏览，却未必足以让循环判断“今天该处理什么”。一个无日期但阻塞同事的任务，可能恰好被按日期筛选的规则漏掉。表 6-8 列出本次试运行需要核对和补齐的数据（其中 `owner` 和 `status` 是原清单已有、需要核对口径的字段），用来表达原先由使用者凭记忆补上的身份、依赖和来源关系。
**表 6-8  每日待办试运行的数据字段与用途**

| 字段 | 为什么需要 |
|------|------------|
| `source_task_id` | 稳定引用来源清单中的同一项工作，不靠标题匹配 |
| `owner` | 判断是否属于当前使用者，缺失时提醒 |
| `due_at` | `YYYY-MM-DD` 截止日期；若来源提供时分秒，先按业务时区归一化 |
| `status` | 区分未开始、进行中、阻塞、完成和取消 |
| `blocks` | 哪些任务依赖它 |
| `updated_at` | 判断资料是否新鲜 |
| `source_url` | 摘要中能回到原任务 |
不必为了补齐表 6-8 的字段，一次整理全部历史记录。第一版只处理本周活动任务，明确标记缺失字段，并转入补充输入的流程，不让模型猜测字段值。

例如一项没有 `due_at` 却在 `blocks` 中关联他人任务的工作，不能仅凭日期为空就排除；系统应保留依赖关系的记录，并请负责人说明下一步如何处理。`updated_at` 用来判断记录是否陈旧，`source_url` 用来回查原任务，两者不能互相替代：能打开链接，不代表读到的是足够新的状态。表中的 `source_task_id` 标识清单里的来源工作项（6.10 骨架中对应样例输入的 `id`，如 `T-104`），与整份摘要的业务身份是两类对象：一份 `daily-plan:2026-08-15` 摘要任务的输入包含当天全部来源任务，`T-104` 更新改变的是这份摘要的输入内容，摘要任务的 `task_id` 不变，获准重做时新建的是 `run_id`。不要把一个来源任务误当成一轮摘要。

这些字段描述的是业务输入要求，前面的最小骨架尚未读取和使用它们。补上字段后，先用下面的发现层演练验证候选集合是否改变，再接生成；否则，表中记录了依赖关系，筛选仍只看日期，遗漏依然存在。
