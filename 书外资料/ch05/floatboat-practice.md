# Floatboat 练习：按钮级操作清单

> 编号说明：本文件由原第 6 章外移，保留原稿表号与小节号（表 6-x 对应新版正文表 5-x；6.x 对应新版 5.x）。

### 方案一：Floatboat，从单次草稿到定时安排

Floatboat 是承载 Agent 的桌面工作环境，可以在会话中处理本地资料，把任务目标与日程保存为 Automation，并查看运行及结果。它适合本章这种来源少、只生成个人草稿的起步任务：先验证摘要，再让同一目标按时启动，不必先写代码或编排节点。

本节只走 **Automation 目标加日程** 路线。另一种 Workflow Trigger Binding 把触发安排绑定到已有工作流，与这里的任务对象不同，管理步骤也不同。等一次任务通过对话完成、处理规则稳定后，还可以把这段会话整理成 Combo 或 Workflow；第 6 章介绍方法复用，第 8 章说明如何把固定步骤转为不需重复调用模型的执行流程。功能依据见来源说明 `SRC-FB-001`；以下是待读者执行的练习，不是已经完成的实测记录。开始前记下客户端版本、操作系统和工作时区；如果界面与下述入口不符，应先核对版本，不要凭外观相似的按钮猜测操作。

**1. 准备五条样本和独立输出目录。** 在专用练习目录放一份待办文件，包含今天到期、已经逾期、没有日期、等待客户和已取消各一项，保留任务 ID、负责人、状态和来源。日期以练习当天及选定时区为准。另建草稿子目录；把两个完整路径交给当前会话，确认读取清单，不授权整个文档目录，也不连接真实邮箱。工作空间与文件访问隔离是两回事，仍要核对实际授权。

**2. 先在会话里运行一次。** 要求助手仅整理上述文件：到期与逾期项保留原日期，缺日期标为待确认，等待客户的事项不写成今天可完成，取消项列明排除理由。输出另存新版本，不修改输入，不发送、不建外部任务。先看它复述的路径和范围，确认后再执行。

结束后打开实际草稿，逐项对照五条输入，并检查原文件是否未变。记录会话、本次执行时间、输入版本、输出路径及错误；没有独立运行编号时，不让助手编一个。用相同输入再做一次，检查旧稿是否保留。这里会调用模型、写文件并产生成本，只是把影响限制在练习目录，不是无副作用的空跑。

**3. 创建一条先不启用的安排。** 打开日程页的“新建日程”，命名为“每日待办摘要练习”，选择明确的起始日期、08:30、`Asia/Shanghai` 时区和每周一至周五的重复规则。这个预设不自动排除法定节假日，也不自动增加调休的周末，需要时另行调整安排。进入“让 Agent 跟进”，选择练习使用的“Agent 行动空间”，把上一轮验证过的目标、输入输出完整路径和禁做事项填入“发给 Agent 的指令”。选择“只整理材料”，不选择“可直接代办”；这也不意味着所有文件写入都被禁止，草稿仍需实际生成。

跟进时间明确选“开始时”，不要保留默认的“提前 1 小时”，否则日程写着 08:30，Agent 可能在 07:30 开始。把“当前状态”设为“草稿”，保存。此处保存的是自动化配置；它和输出目录里的摘要草稿是两个不同对象。也可以通过会话请求预览、确认后创建，但口头答复不能替代下面的回读。

**4. 重新打开，核对保存结果。** 从日程或任务列表找到刚才的名称，进入“编辑任务”，核对目标、空间、状态、重复规则、时区和实际跟进时间。保存名称及任务标识，避免后续误改同名任务。此时状态应仍为“草稿”，不能把日历上的未来格子当成已启用证据；输入路径或时区不对，先修改再保存。

随后在任务详情选择“立即执行”。该操作会真实入队，不是配置预览；排队中不等于执行完成。已有一轮待执行或运行中时，不连续点击。通过“打开最近运行”查看本次会话和状态，再用“查看结果”或“结果目录”核对文件。只有状态、来源和草稿内容都对得上，才进入定时阶段。

**5. 等待一次真正的日程触发。** 编辑同一任务，把状态改为“已启用”，保存后再次打开核对，并查询下一次计划时间。为便于观察，可以先设为稍后的一个明确时刻，验收后再改回每周一至周五 08:30。不要用手动“立即执行”冒充按时触发。让电脑保持开机、唤醒，客户端保持运行，并保证模型连接可用；到时检查新增运行的计划时间、实际开始结束时间和结果。

本地调度不是关机后仍运行的云服务。当前实现采用排队策略和“最近一次”的错过触发处理，不表示漏掉的每个业务日都会补齐，也不提供业务内容去重。定时运行中被判为可恢复失败的情况有延后重试安排，不能把“失败”一概理解为永不再执行，也不能承诺所有失败都会重试。通知只提示查看，不证明产物通过验收。休眠、断网或错过时刻后，先查记录和已有文件，再决定是否人工补做；设备上的实际恢复行为还要单独演练。

**6. 修改，再暂停和恢复。** 先只把 08:30 改为 09:00，保存后重新打开同一任务，确认目标、路径和任务身份没变，并核对下一次时间。暂停时进入“编辑任务”，把“当前状态”改成“已暂停”，保存并回读。保留一个原定触发时刻作为观察点，检查是否仍有新运行，同时单独检查已入队的实例；暂停后续日程，已入队或正在执行的工作仍会继续。

恢复时先核对资料、授权和漏跑日期，再将同一任务改回“已启用”，保存并确认下一次时间。不要另建同名任务，也不要把详情里的“停用任务”当成这个状态切换：后者走归档路径，对应“启用任务”恢复，删除又是另一个动作。本次练习只改暂停状态，不删除历史。

**7. 单独练习停止本次运行。** 在练习样本的一次排队或执行过程中，先查出该轮 `run_id`，再让助手针对这个编号取消 Automation 运行，并重新查询终态。取消入口处理的是一轮运行，不关闭未来日程；要全部停下，须另做上一项暂停。已经结束的运行不再取消，改为检查结果；无法核实停止情况时标记“状态未知”。取消记录也不代表已经撤销文件写入或外部动作，必须检查已有产物及仍在进行的活动，不手工删除日志来制造“没有发生”。

最终记录配置前后值、任务与运行标识、计划及实际时间、输入输出版本、验收结论和失败处置。没有观察到的触发、恢复或取消结果留为“未验证”，不要填成功。练习完成后可以保持暂停，下一阶段再决定是否长期运行。

这条路线先完成的是有人逐次核对的定时草稿练习，6.5 节的业务任务台账与受控领取还要另行实现。产品每次启动产生的运行编号，应按原类别保留，它与本书台账中的 `run_id` 用途不同。要通过 6.11 节的完整验收，还需为“用户、业务日期和摘要类型”建立稳定业务身份，并把规则版本绑定在任务上，在执行前查询已有输入版本与结果，再由台账和验证规则决定是返回原结果、等待补资料，还是允许一次新的业务执行。产品层留下触发或运行记录，业务层则按自己的台账拒绝重复处理。没有落实这些控制时，保持小样本草稿和人工核对；日程已启用只说明日程生效，完整受控循环上线还要等这些控制到位，需要实现这些机制的读者可继续参考下面两种方案。
