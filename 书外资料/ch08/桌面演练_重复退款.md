# 桌面演练：重复退款

> 来源：原第12章 12.17。对应正文第8章 8.6 节“动作状态未知”；可与附录 A 的故障演练卡互链。

团队在不执行真实资金动作的环境里演练：退款接口完成了操作，但响应在网络中丢失。任务超时，调度器准备重试。

**正确的状态变化**

1. 在发出请求前，为这一次退款意图生成并持久化跨重试稳定的 `refund_request_id`，用 `order_id + refund_request_id` 组成业务幂等键，同时绑定退款类型、批准金额、政策和订单版本；
2. 操作超时后，任务状态进入“动作状态未知”，不能归为普通失败；
3. 控制面创建查询操作，用这次退款意图的 `refund_request_id` 向支付系统读取权威状态。这一步依赖支付侧能按该引用查询，前提是发起退款时已把它作为支付侧可检索的商户引用随请求一并发出；若所用接口只支持按支付侧自己生成的对象编号查询，而响应又在网络中丢失，控制面就无从得知该编号，只能等待支付侧回调并通过对账记录确认结果，而不能假设业务幂等键天然可用作查询键；
4. 若已退款，操作状态记为已确认并保存交易 ID，任务转为完成，不再次提交；
5. 若支付系统明确确认该操作不存在，控制面还要复核原批准是否仍绑定当前订单版本，确认后才能在预算和尝试次数上限内，沿同一 `refund_request_id` 重新发起这次操作；
6. 若仍无法确认，任务转为暂停状态，停止该类自动退款，并在交给财务的接手资料中列出状态未知的操作；
7. 客户通知作为独立任务，等待实际退款结果得到确认；确认前不能声称“退款已完成”。

业务幂等键识别的是“这一次退款”，金额和政策版本则是必须核对的绑定参数。退款已经成功、响应却丢失时，即使政策随后升级，也要沿原 `refund_request_id` 查询原交易，不能换一个政策版本就换键重发。若同一意图的金额或其他参数需要改变，先确认原操作状态，再拒绝冲突请求或进入明确的修订审批流程，不能用新键掩盖旧请求是否已生效。

同一订单的第二笔合法部分退款是另一项业务意图，即使类型和金额与第一笔相同，也应取得新的具名批准和新的 `refund_request_id`，并核对累计已退金额。因此，重试不创造新退款身份，新的退款意图也不会被误当成第一次的结果。

**演练中常见的错误**

常见错误包括：执行 Agent 在对话里说“看起来失败”，系统就直接重试；支付接口支持通用请求 ID，业务系统却每次运行都生成新 ID；退款记录与客户消息由不同循环维护，退款尚未确认，消息就已发出；测试只验证返回码，没有模拟响应丢失。

因此，桌面演练要让系统真正进入未知状态，并观察告警、队列和人工界面的表现。团队口头解释“到时候会查询”不足以证明恢复路径确实存在。
