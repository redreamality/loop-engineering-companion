# 重试风暴的修复与验收步骤

> 来源：原第13章 13.17。对应正文第8章 8.10 节图 8-2。

周一早上，客户系统的 API 对调用限流。共用这一接口的五条循环各自认为是瞬时故障，每项任务最多重试三次；每次运行内的工具客户端又自动重试两次。若每次运行只发一个外部请求，且“重试三次”指初始尝试之外再试三次，那么业务层最多 4 次、工具层每次最多 3 次，1000 项任务的最坏请求数为 `1000 × 4 × 3 = 12000 次`；一次运行若包含多个外部请求，还要按实际调用数继续相乘。这样的请求峰值会使服务更难恢复。

**为什么局部合理会造成全局失控**

系统把客户接口的限流响应当成了各项任务独立发生的暂时故障，没有识别出这是同一共享接口发出的容量告警，于是各项任务按照自己的上限重试；工具客户端的内部重试又与业务调度的重试叠加。这个客户系统接口没有统一熔断，新任务继续进入并立即执行，积压越来越多，固定的退避时间还让所有任务同时再次发出请求。请求拥塞使超时增加，新增超时又触发更多重试，最终既增加了费用，也延长了服务恢复时间。监控只显示错误率，没有显示“外部请求数 / 业务任务数”的放大倍数，因此未能在请求刚开始激增时及时限制调用。

**修复**

1. 先针对客户系统启用共享并发上限和熔断，并确认新增的外部请求降到保护阈值以下；
2. 熔断期间只保存原始信号，不启动高成本任务；检查任务仍可查询，且没有新增运行；
3. 工具适配层提供实际发生的 API 重试记录，由控制面计入任务的总尝试预算；完成后核对运行账与外部请求数是否一致；
4. 在退避中加入随机抖动，避免任务同时恢复请求，并检查恢复窗口内的请求峰值是否仍同步出现；
5. 为高优先级客户任务预留少量容量，普通任务排队；确认关键任务没有超时，普通任务也没有丢失；
6. 服务恢复正常、失败能够正确分类后，逐步增加处理量，根据任务已等待的时间和时效要求安排处理顺序；每提高一档处理量，都要确认该观察窗口内的错误率与时延处于阈值内；
7. 持续监控“外部请求数 / 业务任务数”的放大系数；只有放大系数回到基线，并在一个完整观察窗口内保持稳定，才能关闭事故处理任务。

每项修复都要有上述检查通过的记录，不能只修改配置就宣布完成。配置改动只是开始，验证与止损是否生效要看这些检查项的记录。

重试设计既是成本问题，也是可靠性和安全问题。无限尝试可能让下游服务和费用同时失控。
